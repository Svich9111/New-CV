## 1. Краткий анализ ТЗ

**Что строим.** Telegram Mini App и бот для пар: у каждого партнёра личный ИИ-агент с долговременной памятью; сообщение партнёру проходит конвейер «черновик → одобрение → проверка безопасности → оценка тона → адаптация → контроль смысла → доставка». Стек: React + TypeScript, FastAPI, PostgreSQL с pgvector, Redis. [Факт]

**Ключевые ограничения.**

- Изоляция агентов обеспечивается сервером и базой данных, а не промптом; проверяется тестами при каждом выпуске. [Факт]
- Ни одно сообщение не уходит без нажатия «Отправить». [Факт]
- Адаптация сохраняет смысл не менее чем в 95% случаев на эталонном наборе из 100 ситуаций. [Факт]
- Рынок, языковая модель, команда и бюджет не определены (вопросы 1–3 раздела 13). [Уточнить]

**Ключевая сложность.** Код приложения типовой и хорошо ложится на агентов. Сложность в качестве поведения ИИ: эмпатия, адаптация без искажения смысла, кризисный протокол. Поэтому эталонный набор и его прогон вынесены в отдельный сквозной поток: он стартует на д.1 и является гейтом каждого этапа.

**Что меняет реализация агентами.** Узкое место смещается с написания кода на человека: решения, приёмка гейтов, ключи и аккаунты, проверка на телефонах, работа психолога и юриста. Ускорение по коду — около 50–60%, по настройке промптов и приёмке — 10–20%.

| Тип задач | Кто делает | Ускорение к базе |
| --- | --- | --- |
| CRUD, API, миграции, вёрстка экранов | Агент, человек принимает | −50…60% |
| Интеграции (Telegram, оплата, речь) | Агент, человек даёт ключи и проверяет на устройстве | −40…50% |
| Тесты, CI/CD, инфраструктура как код | Агент | −50% |
| Промпты, память, конвейер адаптации | Агент пишет и прогоняет набор, психолог и автор оценивают | −40…50% кода, оценка качества без ускорения |
| Решения, юридические тексты, пилот | Человек | без ускорения |

## 3. Роли в проекте

В проекте семь агентов Claude Code с раздельными зонами и три роли людей. Агент описывается файлом в `.claude/agents/` репозитория: зона, разрешённые каталоги, правила, критерии готовности.

| Роль | Кто | Зона ответственности |
| --- | --- | --- |
| Оператор | Автор проекта | Решения по открытым вопросам, приёмка гейтов, ключи и аккаунты, проверка на телефонах, набор пар для пилота |
| Психолог | Внешний эксперт | Эталонный набор, шкала уровней проблемы, кризисный протокол, оценка сохранения смысла |
| Юрист | Внешний эксперт | Пользовательское соглашение, политика обработки данных, согласие на чувствительные сведения |
| A0 Оркестратор | Агент | Режет этап на задачи, раздаёт их агентам, ведёт `ROADMAP.md` и журнал решений, сводит ветки, готовит гейт к приёмке |
| A1 Архитектор данных | Агент | Схема БД, миграции, политики доступа на уровне строк, контракт API (OpenAPI) |
| A2 Backend | Агент | FastAPI: авторизация, пары, приглашения, лента, шифрование, удаление и выгрузка данных |
| A3 ИИ-ядро | Агент | Промпты, сборка контекста, конвейер сообщения, память, база знаний, эталонные прогоны |
| A4 Frontend | Агент | Mini App, админ-панель, макеты в виде HTML-прототипа |
| A5 Бот и оплата | Агент | Telegram-бот, приглашения по ссылке, уведомления, подписка и Telegram Stars |
| A6 Проверка | Агент | Автотесты, тесты изоляции, независимое ревью каждого запроса на слияние. Не пишет продуктовый код |
| A7 Инфраструктура | Агент | Docker, сборка и выкладка, окружения, резервные копии, мониторинг |

## 4. Как организована работа агентов

Агент не помнит прошлую сессию, поэтому всё состояние проекта живёт в репозитории, а готовность задачи подтверждается тестами, а не отчётом агента.

**Структура репозитория.**

```
CLAUDE.md              — правила проекта: стек, команды, 7 принципов идеологии, запреты
.claude/agents/        — описания агентов A0–A7
.claude/commands/      — команды: взять задачу, сдать задачу, прогнать эталонный набор
docs/TZ.md             — ТЗ (источник требований ФТ-01…ФТ-27)
docs/ROADMAP.md        — этот план со статусами задач
docs/DECISIONS.md      — журнал решений оператора и архитектурных выборов
docs/tasks/NN.md       — карточка задачи: ФТ, границы, критерии готовности, тесты
api/openapi.yaml       — контракт между сервером и клиентом
backend/  frontend/  bot/  infra/
prompts/               — версии промптов агентов продукта
evals/                 — эталонный набор и скрипты прогона
```

**Цикл одной задачи.**

1. A0 создаёт карточку в `docs/tasks/` с проверяемыми критериями готовности.
2. Агент-исполнитель работает в отдельной ветке и отдельном рабочем каталоге (git worktree), чтобы параллельные агенты не мешали друг другу.
3. Сначала пишутся тесты по критериям, затем код. Линтер, типы и тесты запускаются автоматически после правок.
4. Агент открывает запрос на слияние. Сборка прогоняет тесты, тесты изоляции и, если затронуты промпты, эталонный набор.
5. A6 делает ревью в новой сессии, без контекста разработки: сверяет с карточкой и ТЗ.
6. A0 сливает ветку и обновляет статус в `ROADMAP.md`. Гейт этапа принимает оператор.

**Жёсткие правила в CLAUDE.md.**

- Ключи и токены — только в переменных окружения; в репозиторий не попадают.
- Агенты работают только с выдуманными данными. Доступа к продуктивной базе и перепискам у них нет.
- Любой запрос к личным данным идёт через слой доступа с проверкой владельца; прямой SQL в обработчиках запрещён.
- Контракт API меняет только A1; остальные предлагают изменение через карточку.
- Изменение промпта — новая версия файла и прогон эталонного набора; без прогона слияние закрыто.
- Миграции БД, выкладка в продуктив и платёжные настройки выполняются только после подтверждения оператора.
- Агент не отмечает задачу готовой при красных тестах и не отключает тесты, чтобы пройти сборку.

**Параллельность.** Одновременно работают до 3–4 агентов: обычно A2, A3, A4 и один из A5–A7. Больше не даёт выигрыша: оператор не успевает принимать результаты. Frontend работает на заглушках по контракту API до готовности сервера.

## 10. Синхронизация

Ритм задаёт оператор: два окна в день и гейт в конце каждого этапа.

- **Утро, 30 минут.** A0 показывает статус по `ROADMAP.md`, оператор запускает задачи дня и выдаёт недостающие ключи и решения.
- **Вечер, 1–2 часа.** Оператор смотрит запросы на слияние, прошедшие ревью A6, проверяет тестовый стенд на телефоне, записывает решения в `DECISIONS.md`.
- **При каждом изменении промптов.** Прогон эталонного набора; отчёт сравнивается с предыдущей версией.
- **Раз в неделю.** Психолог смотрит выборку из 20 ответов агента на эталонных ситуациях.
