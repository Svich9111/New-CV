## 4. Дефекты

- [MINOR] D-1 `backend/app/bot/webhook.py:70-74`: `json.loads` ловит только `ValueError`. На глубоко
  вложенный JSON (`b"[" * 200_000`) падает `RecursionError`, и вебхук отвечает 500, хотя по
  критерию 4 неверный JSON — 200. Telegram будет повторять доставку. Дойти до этого места можно
  только с верным секретом (без секрета — 403, это проверено), поэтому последствия малые.
  Ожидание: ловить и `RecursionError`, или любое исключение разбора, и отвечать 200.
  Тест: `test_deeply_nested_json_is_ignored` (xfail strict).
- [MINOR] D-2 `backend/app/bot/webhook.py:74-84`: повтор, который приходит, пока первая доставка
  ещё ждёт Bot API, получает 200 «duplicate». Если первая потом ловит временный сбой (502), она
  снимает отметку и отвечает 503. Получается пара `[200, 503]`: если Telegram уже закрыл первое
  соединение, обновление потеряно. Это то же, что A6 m2, здесь — воспроизведение через
  `asyncio.gather`. Тест: `test_duplicate_during_inflight_transient_failure_is_not_lost`
  (xfail strict).

Замечания, которые дефектами не считаю:

- Тайм-аут чтения даёт 503 и снятие отметки, поэтому возможен второй ответ на `/start`. Карточка
  это разрешает; A6 m1 уже требует учесть это в 3.5.
- Ответ Bot API `200` с телом не-JSON (страница прокси) считается постоянной ошибкой: 200, ответ
  на `/start` теряется. Это редкий случай, последствие — пользователь повторит `/start`.
- Пробелы вокруг секрета: через ASGI это 403. При работе через uvicorn/h11 пробелы по краям
  значения заголовка срезаются по RFC 9110, так что `" секрет "` совпадёт. Секрет при этом
  должен быть известен, поэтому проблемы безопасности нет.
