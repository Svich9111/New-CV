## 4. Дефекты

- [MINOR] D-1 `backend/app/bot/webhook.py:70-74`: `json.loads` ловит только `ValueError`. На глубоко
  вложенный JSON (`b"[" * 200_000`) падает `RecursionError`, и вебхук отвечает 500, хотя по
  критерию 4 неверный JSON — 200. Telegram будет повторять доставку. Дойти до этого места можно
  только с верным секретом (без секрета — 403, это проверено), поэтому последствия малые.
  Ожидание: ловить и `RecursionError`, или любое исключение разбора, и отвечать 200.
  Тест: `test_deeply_nested_json_is_ignored` (xfail strict).
- [MINOR] D-2 `backend/app/bot/webhook.py:74-84`: повтор, который приходит, пока первая доставка
  ещё ждёт Bot API, получает 200 «duplicate». Если первая потом ловит временный сбой (502), она
  снимает отметку и отвечает 503. Получается пара `[200, 503]`: если Telegram уже закрыл первое
  соединение, обновление потеряно. Это то же, что A6 m2, здесь — воспроизведение через
  `asyncio.gather`. Тест: `test_duplicate_during_inflight_transient_failure_is_not_lost`
  (xfail strict).

Замечания, которые дефектами не считаю:

- Тайм-аут чтения даёт 503 и снятие отметки, поэтому возможен второй ответ на `/start`. Карточка
  это разрешает; A6 m1 уже требует учесть это в 3.5.
- Ответ Bot API `200` с телом не-JSON (страница прокси) считается постоянной ошибкой: 200, ответ
  на `/start` теряется. Это редкий случай, последствие — пользователь повторит `/start`.
- Пробелы вокруг секрета: через ASGI это 403. При работе через uvicorn/h11 пробелы по краям
  значения заголовка срезаются по RFC 9110, так что `" секрет "` совпадёт. Секрет при этом
  должен быть известен, поэтому проблемы безопасности нет.

### Дефекты раунда 2

- [MINOR] D-3 `backend/app/bot/webhook.py:97-121`: отметку снимают или завершают только ветки
  `except TimeoutError / BotApiError / Exception` и успешный путь. `asyncio.CancelledError` не
  наследуется от `Exception`. Если задачу обработчика отменят, пока идёт `handle_update`, не
  вызовется ни `complete`, ни `release`. Тогда `update_id` навсегда останется «в работе»: каждый
  повтор ждёт `HANDLE_DEADLINE_S` и получает 503. Воспроизведено: после отмены три повтора дали
  `[503, 503, 503]` и ни одного нового `sendMessage`, ответ на `/start` потерян. Запись уйдёт только
  при вытеснении (10 000 записей). Uvicorn не отменяет обработчик при обрыве соединения, а при
  остановке процесса пропадает и вся память, поэтому на практике это маловероятно. Ожидание:
  `try/finally` или `except BaseException: updates.release(update_id); raise`, чтобы при отмене
  отметка снималась. Тест: `test_cancelled_first_delivery_does_not_block_update_forever`
  (xfail strict).

Замечания, которые дефектами не считаю:

- Срок ожидания Telegram («порядка минуты») официально не задокументирован. `HANDLE_DEADLINE_S = 20`
  оставляет большой запас, тест требует не больше 30 с.
- При `retry_after` 10 и сроке 20 с второй повтор 429 (`max_retries = 2`) недостижим: 10 + 10 с
  паузы уже равны сроку. Это безвредно: ответ 503, доставка повторится.
- Повтор держит соединение Telegram открытым до 20 с. При шквале повторов одного обновления это
  занимает соединения из `max_connections` (по умолчанию 40). Последствие — только задержка.
- `description` очищается по шаблону токена, а не по самому значению из настроек. Telegram токен в
  описание не вставляет, шаблон покрывает формат `id:секрет`.
