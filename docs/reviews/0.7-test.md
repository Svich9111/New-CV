## 3. Дефекты

- **D-1 [BLOCKER]** `backend/migrations/versions/0001_initial_schema.py:780` (`pm_update`). Политика
  проверяет только «автор или получатель — я» и не ограничивает, какие колонки меняются.
  Получатель переписывает `author_id` на третье лицо и подменяет `original_enc`
  (`test_recipient_cannot_forge_author`, `test_original_is_immutable`). Автор меняет `recipient_id`/`couple_id`
  на постороннего, и тот читает сообщение (`test_author_cannot_redirect_message_to_outsider`: у Ольги `count = 1`).
  Это нарушает критерий 4 карточки и ТЗ §2 п.2, §4.3 п.3 (сохраняется версия, одобренная автором), ФТ-08, ФТ-10, §7
  («читают оба участника пары»). Ожидается: `author_id`, `recipient_id`, `couple_id`, `original_enc` неизменяемы
  для `feelings_app` (колоночные права `GRANT UPDATE (status, read_at, …)` или триггер); правка
  `adapted_enc`/`is_adapted`/`tone_score` — только конвейером, не получателем.
- **D-2 [MAJOR]** `0001_initial_schema.py:647, 653, 658, 667, 688`. В функциях SECURITY DEFINER указано
  `SET search_path = public` без `pg_temp` в конце. У `feelings_app` есть право TEMP на БД (PUBLIC по умолчанию), а
  `pg_temp` неявно просматривается первым. Тогда временные таблицы `couple_members`/`couples` подменяют настоящие
  внутри `app_is_member`/`app_is_active_member`. Посторонняя видит чужую пару и её подписку
  (`test_definer_functions_cannot_be_hijacked_by_temp_tables`: `(1, 1)`) и отправляет сообщение в чужую пару
  (`test_temp_table_hijack_cannot_send_into_foreign_couple`). Нужен доступ к выполнению произвольного SQL
  (инъекция), но RLS как раз и защищает на такой случай (ТЗ §9.2 п.1, риск Р6). Ожидается:
  `SET search_path = public, pg_temp` (или `pg_catalog, public, pg_temp`) и полные имена `public.<table>` в
  телах функций; дополнительно `REVOKE TEMPORARY ON DATABASE … FROM PUBLIC`.
- **D-3 [MAJOR]** `backend/app/db.py` (`user_scope`) и `.env.example:3`. Роль `feelings_app` — NOLOGIN, отдельной
  LOGIN-роли для приложения нет, шаблон подключения — суперпользователь `postgres`. Поэтому внутри `user_scope`
  выполняются `SET LOCAL ROLE postgres` и `RESET ROLE` (`test_user_scope_cannot_escape_role`), и любой запрос
  вне `user_scope` идёт в обход RLS. Изоляция держится на дисциплине кода, а не на БД (АР-7, ТЗ §9.1 п.5,
  §9.2 п.4). Ожидается LOGIN-роль приложения без superuser, которая входит только в `feelings_app`
  (работоспособность схемы подтверждает `test_dedicated_login_role_cannot_escape_to_superuser`), и
  соответствующий `FEELINGS_DATABASE_URL` в шаблоне и `infra/`. Миграции — под отдельной ролью-владельцем.
- **D-4 [MINOR]** `0001_initial_schema.py:752, 791, 736`. `app_is_member` возвращает true и для бывших участников
  (сделано ради чтения истории, Д7), но им же проверяются записи. Бывший участник выпускает приглашение в
  прежнюю пару (`test_former_member_cannot_invite_into_former_couple`), меняет подписки и платежи прежней пары,
  ставит ей `dissolved`. ТЗ §4.5 п.2: обмен прекращается. Ожидается: в `WITH CHECK` для `invites` и
  `subscriptions`/`payments` проверять `app_is_active_member(couple_id, app_uid())`.
- **D-5 [MINOR]** `0001_initial_schema.py:726` (`users_self FOR ALL`). Пользователь может переписать свой
  `telegram_id` (`test_user_cannot_change_own_telegram_id`). Тогда человек с этим telegram_id при входе
  (`app_upsert_user`) попадает в чужую учётную запись (ФТ-01). Ожидается: `telegram_id` (и `id`, `created_at`)
  неизменяемы для `feelings_app` (колоночные права UPDATE).
- **D-6 [MINOR]** `0001_initial_schema.py:657`. `app_is_active_member(p_couple, p_user)` и `app_couple_has_members`
  выданы `feelings_app` с произвольными аргументами. Это оракул: можно проверить, состоит ли пользователь X в
  паре Y (`test_membership_oracle_not_available_for_foreign_users`), а ТЗ §7 / §9.2 п.2 этого не допускают.
  Ожидается: функции политик не принимают чужого пользователя (сравнение с `app_uid()` внутри) или
  недоступны для прямого вызова.
- **D-7 [MINOR]** `0001_initial_schema.py:671–678`. Для telegram_id с `deleted_at IS NOT NULL` функция
  `app_upsert_user` молча возвращает NULL: `ON CONFLICT DO NOTHING` срабатывает, а повторный SELECT
  отфильтровывает строку. Удалившийся пользователь не может войти снова до физического удаления строки
  (`test_upsert_user_after_soft_delete_returns_account`; ФТ-21, ФТ-04 «повторное создание»). Ожидается явное
  поведение: новая учётная запись или ошибка, которую обрабатывает 1.1.
- **D-8 [MINOR]** `api/openapi.yaml:176–178, 685`. Поля `inviter_name` (`GET /invites/{token}`) и
  `Couple.members[].name` нельзя заполнить под текущими политиками: `users_self` не даёт партнёру и
  приглашённому прочитать имя (подтверждено `test_partner_and_outsider_cannot_read_by_direct_id[users]`), а
  функции SECURITY DEFINER для имени нет. Ожидается функция, отдающая только имя участника своей пары или
  автора приглашения (можно в 1.3), либо правка контракта.
- **D-9 [MINOR, тесты]** `backend/tests/test_rls_isolation.py:121` (и строки для `conversations`, `message_drafts`).
  Запросы с `JOIN agents` не обнаруживают отключённый RLS на самой дочерней таблице (см. мутационную проверку).
  Ожидается проверка по прямому `id`/`agent_id` без соединения. В A8 такая проверка есть:
  `test_partner_and_outsider_cannot_read_by_direct_id`.

Наблюдение (не дефект 0.7, для 1.x / ФТ-21). После удаления аккаунта пара остаётся `active` с одним участником.
Это противоречит §7 «ровно две записи на активную пару». Обработчик удаления должен расторгать пару.
Кроме того, каскад удаляет и сообщения, которые партнёр отправил удалённому пользователю, а судьба истории
по §7 пока «[уточняется]».

### Новые дефекты

- **D-10 [MINOR]** `0001_initial_schema.py:965` (`invites_insert`). Продлить срок приглашения обновлением нельзя (m5),
  но создать сразу «вечное» можно: `expires_at = now() + 10 years` проходит. ТЗ §4.1 п.6, ФТ-03: ссылка действует 7 дней.
  Тест `test_invite_lifetime_is_limited_to_seven_days` — xfail. Ожидается: `CHECK`/`WITH CHECK`
  `expires_at <= now() + interval '7 days'` либо создание приглашения функцией (можно в 1.3). Там же `used_by`
  задаётся при INSERT произвольно; само по себе это безвредно, так как статус `active`.
- **D-11 [MINOR]** `0001_initial_schema.py:989` (`drafts_update`). Владелец меняет любой статус черновика, кроме `sent`.
  Черновик, остановленный проверкой безопасности (`blocked`), переводится в `approved` и уходит через
  `app_send_draft`. Тест `test_blocked_draft_cannot_be_unblocked_and_sent` — xfail. Контракт `POST /drafts/{id}/send` (422
  `blocked_by_safety`), ТЗ §9.3. Повторная проверка конвейером (`pipeline_withhold`) остаётся вторым рубежом,
  поэтому MINOR. Ожидается: статус `blocked` не снимается приложением (колоночные права без `status` плюс функции
  одобрения/отклонения, либо `WITH CHECK`, запрещающий выход из `blocked`).

Наблюдения (не дефекты): `app_couple_feed` не фильтрует по паре, поэтому у человека, создавшего новую пару,
в ленте будет и история прежней (Д7 допускает чтение; уточнить для 1.x). Миграция создаёт `feelings_api` только если
роли нет и не приводит атрибуты уже существующей роли (NOINHERIT, NOSUPERUSER) к нужным. В 0.8 стоит закрепить это
в инфраструктуре; тест `test_roles_have_no_bypass_and_own_nothing` это проверяет.
