## 2. Разбор по вопросам

### 2.1. Можно ли вызвать функции бота не из-под `feelings_billing`

Проверено на 5433 под ролью входа `feelings_api`, в откатываемых транзакциях:

| Попытка | Результат |
| --- | --- |
| `SET ROLE feelings_billing` / `SET LOCAL ROLE` после `SET LOCAL ROLE feelings_app` | `permission denied to set role` |
| `set_config('role','feelings_billing',true)` | `permission denied to set role` (тот же обработчик `check_role`, членство сессионного пользователя) |
| `SET SESSION AUTHORIZATION feelings_billing` | отказ |
| `app_bot_payment_lookup` под `feelings_api` и под `feelings_app` | `permission denied for function` (42501) |
| `pg_has_role('feelings_api','feelings_billing','SET')` | `false` |

Обёртки SECURITY DEFINER (проверено суперпользователем на временных функциях, с откатом):
- обёртку от владельца вызывает `feelings_app`, обёртка зовёт `app_bot_payment_lookup` → `billing role only`. EXECUTE проверяется у владельца, но `current_setting('role')` остаётся ролью, которую выбрал вызывающий. Вложенный вызов из функций пользователя к функциям бота не пускает;
- `set_config('role', …)` внутри SECURITY DEFINER → `cannot set parameter "role" within security-definer function`. Сменить роль внутри функции владельца нельзя;
- та же обёртка, вызванная из `SET LOCAL ROLE feelings_billing`, проходит. Это ожидаемо: у `feelings_billing` EXECUTE есть только на четыре функции бота.

`SET ROLE` и `SET LOCAL ROLE` для проверки равнозначны: проверяется только значение GUC `role` в момент вызова, а установить его может лишь член роли с SET. `RESET ROLE` даёт `none`, вызов получает 42501. Функция с `SET role = …` в `proconfig` тоже проверяет членство сессионного пользователя (PG16). Роли `feelings_app`, `feelings_api`, `feelings_worker`, `feelings_admin` стать `feelings_billing` не могут. Это так, пока ни у одной из них нет членства в роли, и именно здесь пробел (MAJOR-1).

Тело каждой из четырёх функций проверено по `pg_proc.prosrc`: в каждой есть `billing role only`, незаменённых маркеров `--…--` нет ни в одной функции 0017/0019.

### 2.2. Создание роли кластера в миграции

- Повторный запуск и вторая БД в том же кластере: `IF NOT EXISTS` и проверка атрибутов. `GRANT` идемпотентен. ✅
- Downgrade роль не удаляет, отзывает только EXECUTE и USAGE. Обоснование — роль общая для кластера, как в 0001. ✅
- Атрибуты `LOGIN/INHERIT/SUPERUSER/CREATEROLE/CREATEDB/REPLICATION/BYPASSRLS` проверяются. **Членства не проверяются** (MAJOR-1).
- Под владельцем схемы с `CREATEROLE` (PG16) `CREATE ROLE` даёт владельцу ADMIN, а значит путь `init-owner.sql` → `alembic` работает. Тест этого пути нет: в `test_owner_migrations` роль к моменту прогона уже существует в кластере, ветка `CREATE ROLE` под не-суперпользователем не исполняется (MINOR-5).

### 2.3. Тела через importlib из 0017

`_sub` требует ровно одно вхождение (`CREATE FUNCTION`, старый расчёт начала, блокировка счёта), так что правка 0017 не пройдёт молча. Маркеры `--SERVICE_ONLY--`, `--USER_KNOWN--` и `--USER_KEY_SHARE--` подставляет `str.replace` без проверки (0019:236-239). Если маркера нет, проверка роли из тела функции исчезнет. Защитит только EXECUTE и тест, который проверяет лишь `PRECHECK` (MINOR-3). Downgrade восстанавливает тела 0017 из того же модуля, они совпадают с исходными. Для неизменяемых ревизий риск приемлем.

### 2.4. Порядок блокировок (АР-13/АР-38)

Счёт теперь берёт пользователя `FOR KEY SHARE`, затем пару `FOR NO KEY UPDATE`, затем `payments`. Порядок тот же, что у пробного периода, зачисления и возврата. Выход и удаление аккаунта: пользователь `FOR UPDATE` (0002/0005), затем пара. Блокировки `FOR KEY SHARE` на пользователе между собой не конфликтуют, у счёта нет захватов после пары по чужим пользователям, поэтому цикла нет. С конвейером (`FOR KEY SHARE` пары, 0013) и выгрузкой (0006) `NO KEY UPDATE` не конфликтует. Вставка в `payments` берёт `KEY SHARE` пары, которая уже удерживается. ✅ Гонка с удалением аккаунта плательщика в обоих порядках покрыта тестом.

### 2.6. Начало периода и статус

- Новое начало периода — `coalesce(covered_until(now()), now())`. Внутри цепочки поведение прежнее. Разрыв в середине (возвращён средний период) заполняется точно. Разрыв от `now()` короче оплаченного срока перекрывается следующим периодом, и дни перекрытия теряются (MAJOR-2).
- Статус после распада соответствует контракту. Крайний случай — новая активная пара без своего периода (MINOR-1).

В АР-50 п.4 и в docstring это названо «перекрытие допустимо», но потеря оплаченных дней не названа. — Ожидание (решает A1/A0): либо (а) конец нового периода = `v_start + period_days + длина перекрытия с будущими периодами` (или эквивалент: период заканчивается там, где набрано `period_days` непокрытых дней), плюс тест с разрывом короче срока; либо (б) явно записать в АР-50 п.4 и в контракте, что дни, перекрытые будущим периодом, теряются, и вынести это оператору вместе с вариантом «сдвигать следующие периоды».
