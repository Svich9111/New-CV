## 1. Безопасность `roles.sql`

| Вопрос | Вывод |
| --- | --- |
| Пароли в журнале сервера | Под суперпользователем `SET LOCAL log_statement = 'none'`, `log_min_duration_statement = -1`, `log_min_error_statement = 'panic'` **до** первого запроса с паролем. Без суперпользователя — предупреждение, выполнение продолжается (MINOR-2). `pg_stat_statements` не учтён (MINOR-1) |
| Пароли в выводе | `\set QUIET on`, `-X`; проверка формата пароля возвращает только `boolean` через `set_config`; ошибки пароля не содержат. Тест проверяет отсутствие пароля в stdout и stderr, в том числе при ошибках ввода |
| SQL-инъекция | Имена: регулярное выражение `^[a-z_][a-z0-9_]{0,62}$` и запрет `feelings_*`/`pg_*` **до** DDL, затем `format('%I')`. Пароли: `^[A-Za-z0-9_-]{32,}$` и `format('%L')`. Переменные psql везде подставляются как `:'…'` (литерал). Пути инъекции не нашёл |
| Одна транзакция, `dry_run` | `BEGIN` … `COMMIT`/`ROLLBACK`, `ON_ERROR_STOP` — любая ошибка откатывает всё; `dry_run` выполняет всё и откатывает (тест есть) |
| NOINHERIT и членства | Роли входа — `LOGIN NOINHERIT NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS`, членства — `INHERIT FALSE, SET TRUE` (синтаксис PG16). Итоговая проверка: `pg_has_role(…, 'MEMBER')` с учётом вложенных членств — только разрешённые роли; `'USAGE'` — ни одной (права не наследуются); `'SET'` — на все нужные. Роль воркера не может стать `feelings_admin`, а уже существующая роль с лишним членством останавливает скрипт (тест). `BYPASSRLS` нет ни у ролей входа, ни у групповых ролей |
| Защита существующих ролей | Существующая роль с `SUPERUSER`/`CREATEROLE`/`CREATEDB`/`REPLICATION`/`BYPASSRLS` не трогается; имена `feelings_*`, `postgres`, `Bad-Name` отклоняются (тест) |
| АР-10 | `feelings_api` — только `feelings_app` (проверяется для `feelings_api` при каждом запуске); у админ-API и воркеров свои роли входа |

Принятый риск (не замечание): роль входа воркера может стать `feelings_app` и выставить `app.user_id` любого
пользователя. Это то же доверие, что у API, и оно заложено в АР-36 (воркер работает от имени владельца). В
ADMIN.md стоит прямо сказать, что пароль воркера по ценности равен паролю API.

## 2. Docker Compose, Dockerfile, Makefile, CI

- Порядок `postgres (healthy) → migrate (completed) → db-roles (completed) → worker-*` выдержан; пустой пароль
  останавливает `db-roles`, и воркеры не стартуют. Портов у новых сервисов нет, БД и Redis — на `127.0.0.1`.
- Dockerfile: пользователь без прав (`uid 10001`); зависимости ставятся по `uv.lock` без инструментов разработки;
  `.dockerignore` пускает в контекст только `backend/` и `prompts/`, `.env` исключён — секретов в образе нет.
  Путь промптов `/srv/prompts` совпадает с `DEFAULT_PROMPTS_DIR` (`parents[3]`).
- Makefile: `dev-up`/`dev-down`/`db-roles` с `--env-file .env --profile workers`. CI печатает `psql --version`
  (тест требует psql ≥ 15).

## 3. `docs/ADMIN.md` против АР-33, АР-36…АР-39 и §9.1

Полно и верно: чек-лист продуктива, переменные по процессам, роли и порядок `alembic → roles.sql`, ротация
паролей, ключи шифрования (порядок «добавить → перезапустить → сделать текущим», хранение отдельно от копий
БД), ключ отпечатков «не удалять никогда» (АР-36/37), токены администратора (≥ 32 байт, только SHA-256, ротация
без простоя; АР-39), контакты помощи (АР-33), `FEELINGS_ENV`, хранение в РФ и закрытые порты (§9.1).
Неточности — MINOR-3…MINOR-5.

## 4. Тест `test_login_roles.py`

- Временные роли `t_wlogin_*`/`t_alogin_*` удаляются в `finally` с проверкой, что их не осталось. Снимок
  групповых ролей, их членств и хеша пароля `feelings_api` до и после — равны: общие роли `feelings_*` не
  меняются (CLAUDE.md).
- Проверки фактические: атрибуты и опции членств, вход по паролю, `permission denied` без `SET ROLE`, доступные и
  запрещённые `SET ROLE`, области `worker_scope`/`user_scope`/`admin_scope`, ротация, лишнее членство, плохой
  ввод, зарезервированные имена, `dry_run`.
- **«0 или 1» захваченных задач** (`memory_claim_extraction`, `memory_claim_compaction`, `kb_claim_index`) — допустимо:
  проверяется право EXECUTE под `feelings_worker`, а не логика захвата (её проверяют `test_memory_*`,
  `test_kb_index`). Транзакция откатывается, аренды не остаются. Точнее было бы проверять отсутствие ошибки прав
  вместо значения, но ослаблением это не является.
- Путь `FEELINGS_API_DB_PASSWORD` не проверяется вовсе (MINOR-6).

## 5. Замечания

BLOCKER и MAJOR нет.

- [MINOR-1] infra/db/roles.sql:62-69 — если на сервере загружен `pg_stat_statements` с
  `pg_stat_statements.track_utility = on` (по умолчанию), текст `ALTER ROLE … PASSWORD '…'`, собранный `\gexec`,
  может сохраниться в статистике. Нормализация констант в служебных командах зависит от версии; полагаться на неё
  не стоит. Ожидание: под суперпользователем ещё `SET LOCAL pg_stat_statements.track_utility = off`, если модуль
  загружен (проверка `current_setting('pg_stat_statements.track_utility', true)`), и строка об этом в
  ADMIN.md §1 п.8.
- [MINOR-2] infra/db/roles.sql:67-69 — без суперпользователя скрипт только предупреждает и **продолжает**, хотя
  пароль может попасть в журнал (`log_statement = ddl/all`). Безопаснее остановиться, если не передано явное
  согласие (`-v allow_logged=1`) или если `current_setting('log_statement')` ∈ (`ddl`, `all`), — значение
  настройки роль прочитать может.
- [MINOR-3] docs/ADMIN.md §5 — «переписывает её без удалённого и снимает пометку **только воркер памяти**» —
  неточно. Первым это делает фоновая `run_forget` в процессе API (если модели созданы), а воркер — запасной путь
  через сжатие. Без работающей модели и сжатие не обнуляет помеченные сводки (`run_compaction` выходит с ошибкой
  на `build_profile` до записи). Сводки при этом остаются **скрытыми**, утечки нет, теряется только непрерывность.
  Исправить формулировку и добавить: воркер памяти без `OPENROUTER_API_KEY` не стартует (`_main` создаёт модели
  при запуске), поэтому в compose при пустом ключе `worker-memory` уходит в цикл перезапусков
  (`restart: unless-stopped`) — для разработки без кредитов это ожидаемо, но должно быть описано.
- [MINOR-4] docs/ADMIN.md — нет пунктов:
  - (a) пароль роли входа воркера по ценности равен паролю API (может действовать от имени любого пользователя
    через `feelings_app`);
  - (b) `docker compose config` и `docker inspect` показывают пароли из `.env` (URL воркера собирается в
    compose) — не прикладывать их вывод к тикетам;
  - (c) АР-39: материалы базы знаний — только при подтверждённом `rights_basis`, настоящие книги — после решения
    оператора (§6.4 «[уточняется]»);
  - (d) запуск `roles.sql` без `-a`/`-e`/`-E` у psql: эти ключи печатают запросы вместе с паролем.
- [MINOR-5] docs/ADMIN.md — резервное копирование (§10: ежедневно, 30 дней, проверка восстановления раз в
  квартал) упомянуто только для ключей. Дать ссылку на задачу 4.7 или раздел-заготовку, чтобы чек-лист продуктива
  был полным.
- [MINOR-6] backend/tests/test_login_roles.py — ветка `FEELINGS_API_DB_PASSWORD` (`ALTER ROLE feelings_api …`) не
  выполняется ни одним тестом. Безопасный способ — `-v dry_run=1` с паролем API: изменение откатывается, а снимок
  ролей и хеш пароля `feelings_api` проверяются как сейчас.
- [MINOR-7] infra/backend.Dockerfile:5-6 — базовые образы `python:3.12-slim` и `ghcr.io/astral-sh/uv:0.11.32`
  закреплены по тегу, а не по дайджесту. Для образа разработки допустимо; для продуктивного (4.7) — закрепить
  `@sha256:…`.
