## 4. Негативные сценарии из ТЗ

- **Поддельные данные.** `turn_id` несуществующей реплики и ответа агента вместо реплики владельца — 0 событий, отметки
  нет. Чужой текст под ключом три раза подряд — 422, аренды не остаётся. Огромный `Retry-After` и часы, ушедшие
  назад, повтора раньше окна не дают. Реплика из пробелов Python не уходит, реплика с буквой уходит без изменений.
- **Чужой владелец.** `record_safety_events` от имени Бориса с `turn_id` реплики Анны возвращает 0: отметка Анны не
  ставится, событий нет ни у Анны, ни у Бориса. Проверено под ролью `feelings_api` (`user_scope`, RLS). Тесты р.2 «один
  ключ у двух владельцев» — зелёные.
- **Истёкший срок.** Окно лимита: до `retryAt` повтора нет, после — есть (у последней реплики). Тесты р.2 «аренда
  истекла посреди ответа» — зелёные.
- **Повторное использование.** 8 одновременных повторов несохранённого кризиса — одно событие, одна реплика. 10
  повторов подряд — тот же ответ. Повтор после отката 0020 — тот же `crisis` без нового события. Четыре POST после
  трёх 422 — четыре разных ключа.
- **Утечка к партнёру.** Изменения 0020 касаются только своих строк (`a.user_id = :u` и RLS). Сверка О-4 читает
  только свою историю (`GET /chat/messages`), записи старых страниц в ленту не встают.
- **Инструкции в тексте сообщения.** Тексты в `safety_events` не попадают (`test_safety_event_text_free`), в журналы
  тоже (A1 `test_logs_have_no_texts_or_keys`). На экране XSS остаётся текстом (тесты р.1 в составе `vitest run`).

## 5. Дефекты

- **[MINOR] A8-2.2-D8** `frontend/src/screens/Chat.tsx:61-86` (`LimitedCaption`) ↔ `frontend/src/chat/session.ts:431-433`
  (`retry`: `if (!turn || turn.key !== key …) return`). Регресс р.3: появился вместе с N5. Подпись «Сохранено.
  Ответа пока нет — лимит закончился, можно повторить.» и кнопка «Повторить» показываются у **любой** реплики под
  лимитом. `retry` молча выходит, если реплика не из последнего обмена.
  - Сценарий: «Первая» → 429 (`Retry-After: 1`), окно прошло, человек пишет «Вторая» → ответ. У «Первой» — «можно
    повторить» и кнопка, нажатие ничего не делает (POST нет, подпись та же).
  - Ожидается: кнопку и «можно повторить» показывать только у реплики, которую `retry` примет (последний обмен).
    Другой вариант — повтор любой реплики под лимитом тем же ключом: сервер по АР-51 ответит на неё. Основание: ТЗ §8
    (состояние и действие понятны), §10, карточка, критерий 6.
  - Тест `Chat.a8r3` «A8-2.2-D8…», `test.fails`. Без `.fails` падает так: `expected 2 to be 3` (POST после нажатия
    нет). На `9410ecc` тест зелёный.
- **[MINOR] A8-2.2-D9** `frontend/src/screens/Chat.tsx:89-134` (`OwnerCaption`) ↔ тот же `session.ts:431-433`. Так
  было и до р.3, раньше не найдено. У прежней реплики «Не отправлено» (и «Сообщение сохранено, ответа нет» /
  «неизвестно») после следующей удачной реплики остаётся кнопка «Отправить ещё раз» / «Повторить» / «Проверить и

  - Реплика остаётся видна, её можно набрать заново, поэтому MINOR. Но кнопка обещает действие, которого нет, и
    человек может решить, что сообщение ушло (ТЗ §2 п.2, §10 «понятное сообщение, реплика не теряется»).
  - Ожидается то же, что в D8: убрать повтор у реплик не из последнего обмена (подпись оставить) или поддержать
    повтор любой своей реплики по её ключу.

будет пересмотреть вместе с этим изменением.

## 6. Замечания (не дефекты)

- **О-5.** `record_safety_events(turn_id=…)` не пишет событие, если реплику удалили в те миллисекунды между вердиктом
  и фоновой записью (ревью р.3, «Замечено» п.2). Кризисный ответ с контактами всё равно уходит. Потеря касается только
  статистики ФТ-17. Согласен с ревьюером: одной фразой в АР-51.
- **О-6.** Отметки `safety_recorded` теряются при откате 0020. Повтор несохранённого кризиса после отката и возврата
  запишет второе событие. Так и описано в 0020, откат — только с подтверждения оператора (АР-4).
