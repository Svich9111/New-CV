## 2. Криптография — разбор

- Примитив: только `cryptography` `AESGCM`, своей криптографии нет. Ключ 32 байта проверяется дважды: `_decode_key` и `Keyring.__init__`.
- Nonce: 12 байт из `os.urandom` на каждую запись, на одном ключе не повторяется (вероятностно). Случайный 96-битный nonce
  ограничивает ключ примерно 2^32 записями (NIST SP 800-38D) — см. MINOR-5.
- AAD: `header + "table|column|uuid"`. Заголовок сам себя разграничивает (в нём есть длина), имена проверяются по `[a-z][a-z0-9_]*`
  (знака `|` в них быть не может), у UUID канонический вид. Склейка однозначна. Версия и id ключа подписаны: подменить id на
  другой ключ набора нельзя (тест `:131` с одним ключом под двумя id это доказывает).
- `_split`: проверены длина, версия, `kid_len > 0`, ASCII и шаблон id, минимальная длина `head + 12 + 16`. Пустой открытый текст
  обрабатывается корректно.
- Ошибки: `DecryptionError(reason)` без текста, `InvalidTag`/`UnicodeDecodeError` гасятся `from None`. `KeyConfigError` называет
  только id ключа и имя переменной, но не значение. Сравнения тегов делает библиотека (за постоянное время); в модуле нет
  сравнений секретов через `==`.
- `reencrypt` сначала проверяет подлинность, затем возвращает запись под текущим ключом как есть: подделку под текущим ключом
  «узаконить» нельзя. `needs_rotation` на битом заголовке бросает `DecryptionError`: для выборки на перешифровку (4.7) это
  допустимо, но 4.7 должна это обработать.
- Набор ключей хранится в `app.state.keyring` и создаётся до движка БД. Тест `:267` подтверждает, что `sessionmaker` при отказе
  не создаётся.

## 3. Решение по AAD оригинала (через `draft_id`)

Защита от перестановки сохраняется: на `partner_messages.draft_id` стоит `UNIQUE` (`0001:337`), черновик в статусе `sent` под
`feelings_app` не меняется (`drafts_update`). Поэтому оригинал одного сообщения в другом не расшифровывается (тест `:608`).
Остаётся оговорка: `draft_id` — изменяемая колонка, а не первичный ключ. Тот, у кого есть прямая запись в БД, может перенести
пару `(original_enc, draft_id)` в чужую строку целиком. При AAD с id сообщения такая подмена была бы отвергнута. Это та же
модель угроз, что и с правкой `couple_id`/`author_id`, поэтому решение приемлемо. Альтернативы (ключ в БД, AAD без id)
отвергнуты правильно.

Последствия Б-38/Б-39 оценены ниже (MAJOR-1, MINOR-1, MINOR-2). Одного бэклога недостаточно, потому что текущий код слоя
доступа превращает одну «осиротевшую» строку в отказ всей ленты.
