## 2. Замечания

### BLOCKER

- **[BLOCKER] B1** `backend/migrations/versions/0001_initial_schema.py:780-782` — политика `pm_update` разрешает автору
  и получателю менять любые колонки `partner_messages` без проверки членства в паре. Проверено запуском:
  (а) Анна под своим `app.user_id` выполнила `UPDATE partner_messages SET recipient_id = <Ольга>, original_enc = 'changed'` —
  посторонняя Ольга сразу читает сообщение. Это отправка в чужую пару в обход `pm_insert`.
  (б) Игорь (получатель) выполнил `SET original_enc = 'forged', author_id = <Ольга>, original_viewed_at = NULL` — подделал
  оригинал, автора и стёр факт просмотра оригинала. Политика UPDATE также не проверяет, что пользователь всё ещё
  активный участник, поэтому после выхода из пары история не «только для чтения» (Д7). Из-за `pm_insert` автор может
  вставить сразу `status='delivered'`, `is_adapted=true` и свой `adapted_enc`, то есть обойти конвейер §6.2.
  — Ожидание: `couple_id`, `author_id`, `recipient_id`, `original_enc`, `sent_at`, `reply_to_id` после вставки не меняются
  (триггер `BEFORE UPDATE` или права на уровне колонок: `GRANT UPDATE (status, read_at, …)`). Отметка прочтения и просмотра
  оригинала — только через SECURITY DEFINER функции (`app_mark_read`, `app_get_original`). Тогда просмотр записывается
  один раз и стереть его нельзя. Результаты конвейера (`adapted_enc`, `is_adapted`, `tone_score`, `delivered_at`) пишет
  только сервисная роль или функция, а не пользователь. `pm_insert` пропускает только `status='processing'`,
  `adapted_enc IS NULL`, `is_adapted=false`. Нужны тесты на каждый из этих обходов
  (ТЗ §2 п.2–3, §6.2 п.2, §7 «Правила доступа», карточка: «нельзя отправлять … в чужую пару»).

### MAJOR

- **[MAJOR] M2** `0001_initial_schema.py:732-733` — у `couples_insert` проверка только `app_uid() IS NOT NULL`.
  Проверено: Ольга выполнила `INSERT INTO couples (status, activated_at) VALUES ('active', now())` и сразу вступила
  в неё инициатором (`members_insert` статус пары не проверяет). Получилась активная пара из одного человека. Тест
  `test_member_cannot_activate_couple_alone` (`test_rls_isolation.py:477-486`) проверяет только UPDATE уже активной
  пары, поэтому дыру не видит. — Ожидание: `WITH CHECK (status = 'pending' AND activated_at IS NULL AND dissolved_at IS NULL)`,
  а в `members_insert` — проверка, что пара `pending`. Нужен тест «INSERT пары сразу в active запрещён» (карточка:
  «активировать пару в одиночку нельзя»; ТЗ §7 «ровно две записи на активную пару»).
- **[MAJOR] M3** `0001_initial_schema.py:730-746` и `app/db.py:38-44` — `INSERT … RETURNING` в `couples` и
  `couple_members` всегда падает с ошибкой RLS. Причина: для RETURNING строка должна пройти SELECT-политику
  `app_is_member()`, а функция STABLE и вставленную строку не видит. Проверено: ORM `session.add(Couple()); flush()`
  внутри `user_scope` падает (SQLAlchemy забирает серверные значения по умолчанию через RETURNING). То же для
  `INSERT INTO couple_members … RETURNING`. Задача 1.3 (`POST /couple`) на ORM не реализуется. — Ожидание:
  создание пары и инициатора — одной функцией SECURITY DEFINER `app_create_couple()` (как вступление), либо поправить
  SELECT-политики. Нужен тест создания пары под `user_scope` через ORM (RoadMap 1.3; CLAUDE.md — слой доступа).
- **[MAJOR] M4** `0001_initial_schema.py:791-795` — `subs_member`/`payments_member` `FOR ALL` для любого участника,
  в том числе бывшего (`app_is_member` учитывает бывших). Проверено: Игорь под своим `app.user_id` перевёл просроченную
  подписку в `active` до 2036 года, вставил платёж `succeeded` от провайдера `fake` и удалил все платежи пары.
  Это прямое нарушение §11: статус подписки должен зависеть только от реальной оплаты. — Ожидание: пользователю на
  `subscriptions`/`payments` только SELECT. Запись — функциями SECURITY DEFINER или отдельной сервисной ролью
  обработчика платежей Telegram Stars (задача 4.4). DELETE платежей запрещён (ТЗ §11 п.1, ФТ-19).
- **[MAJOR] M5** `0001_initial_schema.py:774-775`, `api/openapi.yaml:387-404` — правило §7 «оригинал отдаётся
  получателю отдельным запросом и фиксируется» держится только на коде приложения. Под RLS получатель читает
  `original_enc` любым SELECT, в том числе пока сообщение в статусе `processing`, до адаптации. — Ожидание: отозвать

  `app_get_original(message_id)`, которая отдаёт текст и в той же транзакции ставит `original_viewed_at`). Ленту

- **[MAJOR] M6** `api/openapi.yaml:270-281`, `337-364`, `tables.py:304-317` — в ключевом сценарии §1 «агент Игоря
  подсказывает, как ответить», в §4.4 п.5 и на экране «Ответить с агентом» (§8) нужен ответ на конкретное входящее.

### MINOR

- **[MINOR] m1** `0001_initial_schema.py:646-690` — функции SECURITY DEFINER объявлены с `SET search_path = public`
  без `pg_temp` в конце. По правилам PostgreSQL временная схема для таблиц тогда просматривается первой.
  Проверено: `CREATE TEMP TABLE couple_members …` под `feelings_app` подменяет результат `app_is_member()`,
  и посторонний видит чужую пару и её участников. Практически сейчас это не хуже существующих обходов с той же
  SQL-инъекцией: `user_scope` подключается суперпользователем (`app/config.py:13`), поэтому `RESET ROLE` и
  `set_config('app.user_id', <чужой id>)` тоже проходят — и то и другое проверено. — Ожидание:
  `SET search_path = pg_catalog, public, pg_temp` (или полные имена `public.couple_members`) и
  `REVOKE TEMP ON DATABASE … FROM PUBLIC`. В DECISIONS записать модель угроз: RLS защищает от ошибок логики,
  а не от SQL-инъекции. Для продуктива приложение входит LOGIN-ролью, у которой есть только права `feelings_app`,
