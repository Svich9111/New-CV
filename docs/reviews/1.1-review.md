## 2. Алгоритм initData: сверка с документацией Telegram

Сверено с разделом «Validating data received via the Mini App»:

- `secret_key = HMAC_SHA256(key="WebAppData", msg=bot_token)` — `telegram.py:31-32`: ключ и сообщение стоят в правильном порядке. ✅
- data-check-string: все поля, кроме `hash`, отсортированы по ключу, `key=value` после URL-декодирования, соединены через `\n`. Реализовано в `telegram.py:57`. Поле `signature` (Ed25519 для третьих сторон) входит в строку, как требует документация. ✅
- `hex(HMAC_SHA256(secret_key, dcs))` сравнивается через `hmac.compare_digest` (за постоянное время), hash в верхнем регистре тоже принимается. ✅
- Независимая реализация A6 (кодирование через `quote`, кириллица, `& = +` в имени, `photo_url`, `signature`) проходит проверку, hash в верхнем регистре тоже. ✅
- Повторы: initData можно повторно предъявить в пределах 24 ч, учёта `query_id` нет. Это соответствует ТЗ и карточке (окно 24 ч), отдельным требованием не является. Отмечено как MINOR-7.
- Кодировки: `parse_qsl(strict_parsing=True)` превращает `+` в пробел, некорректный UTF-8 заменяется на U+FFFD. Подпись в таких случаях не сойдётся, и запрос будет отклонён. ✅ Исключение — hash не из ASCII (MAJOR-2).
- Пустой токен бота даёт отказ до любых вычислений. ✅

## 3. Сессия (JWT)

- Алгоритм зафиксирован (`algorithms=["HS256"]`), обязательны `sub, exp, iat, aud`, `aud` проверяется. `alg=none` отклоняется (тест есть). ✅
- Длина секрета не меньше 32 символов проверяется **только при выпуске** (`session.py:17-18`), при чтении (`read_token`) не проверяется. Подделать токен пустым ключом нельзя: PyJWT 2.15 отказывает с `HMAC key must not be empty`, проверено пробой.
- Пустой `FEELINGS_SESSION_SECRET` в продуктиве: сервис **запускается**, вход отвечает **500**, и пользователь при этом уже создан (MAJOR-1). Ожидается одно из двух: запуск падает при `env != dev/test` и пустом или коротком секрете или токене бота; либо секрет проверяется до upsert, и клиент получает ответ в формате Error.
- Отзыв при удалении: `GET /me` после `deleted_at` даёт 401, проверено пробой. Но `current_user_id` (`deps.py:26-35`) проверяет только подпись токена и не проверяет, жив ли пользователь. Будущие эндпоинты будут пускать удалённого пользователя до истечения TTL (1 ч), если сами не проверят его (MINOR-6).

## 4. Замечания

- [MAJOR] `backend/app/api/auth.py:30-35`, `backend/app/core/session.py:17-18` (MAJOR-1). Если `FEELINGS_SESSION_SECRET` пустой или короче 32 символов, `issue_token` бросает `SessionError`. Обработчик его не ловит, поэтому клиент получает 500 `Internal Server Error` не в формате Error. К этому моменту `upsert_by_telegram_id` уже создал строку users (проба: статус 500, создан 1 пользователь). Сервис стартует без проверки секретов. Ожидается: проверка конфигурации при старте (`env` продуктивный → пустой или короткий `session_secret` или пустой `telegram_bot_token` роняет запуск); проверка секрета до upsert; любой отказ в формате Error. Карточка: «При отказе пользователь в БД не создаётся», «Ответы по контракту».
- [MAJOR] `backend/app/core/telegram.py:60` (MAJOR-2). `hmac.compare_digest(expected, received.lower())` на `str` бросает `TypeError`, если в hash есть символы не из ASCII. Запрос `init_data="auth_date=1&hash=%D0%B0"` получает **500** вместо 401 (проверено через API). Ожидается: проверять hash как 64 hex-символа (или сравнивать байты) и при ошибке бросать `InitDataError` → 401 `invalid_init_data`; добавить тест. Карточка: подделанные данные отклоняются; контракт `/auth/telegram` → 401.
- [MAJOR] `backend/app/api/auth.py:31-32` (MAJOR-3). Ответ 403 `account_deleted` не объявлен у `POST /auth/telegram`: в контракте только 200 и 401. Ожидается одно из двух: предложить A1 через карточку добавить в контракт 403 (или 401 с кодом `account_deleted`) и `Validation` (422); либо вернуть код, который в контракте есть. Критерий «сохраняется только telegram_id, имя не сохраняется» тестом не подтверждён: initData содержит `first_name`, но `me.name is None` и пустота остальных колонок не проверяются.
