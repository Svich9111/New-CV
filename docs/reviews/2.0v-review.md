## 2. Ответы на особые вопросы

- **SECURITY DEFINER и `search_path`.** У четырёх функций `search_path = public, pg_temp`, все объекты пишутся с
  префиксом схемы (`public.vector`, `OPERATOR(public.<=>)`), `REVOKE … FROM PUBLIC`, затем `GRANT` ровно нужной
  роли. Владелец — `postgres`, как у функций 0001–0007; это прежнее соглашение проекта, новым замечанием не
  считаю. `embedding_arg` не definer и без EXECUTE у ролей: вызывается только изнутри функций от имени владельца.
  Под `feelings_app` она недоступна (проверено тестом прав).
- **Ошибки без значения вектора.** Ошибка разбора pgvector (в её тексте есть сам литерал) перехватывается
  `EXCEPTION WHEN OTHERS` и заменяется на `22023 'bad embedding'`; `CONTEXT` PL/pgSQL параметров не содержит.
  Параметры запроса попадут в журнал сервера только при включённых `log_parameter_max_length*` — оставить их
  выключенными в продуктиве (заметка для 0.8/эксплуатации).
- **HNSW и добор.** Выдача всегда полная (`min(предел, подходящих)`): HNSW в pgvector 0.6 фильтрует после обхода
  графа (не больше `ef_search` кандидатов), поэтому недобор ловится сравнением `cardinality` и закрывается точным
  перебором. Для памяти при тысячах агентов HNSW почти никогда не наберёт записей одного агента, и реально
  работает перебор по `agent_id`. Для объёмов одного агента (сотни–тысячи записей) это миллисекунды: решение
  разумное, при pgvector ≥ 0.8 нужен iterative scan (записано в АР-35). `plan_cache_mode = force_custom_plan` в
  функции нужен, чтобы план строился под фактические параметры — верно.
- **`kb_nearest`.** Фильтры по меткам корректны: пустой массив тем — без фильтра; уровень вне 1–5 — 22023;
  фрагменты без уровня при фильтре не попадают. Только `indexed`, только та же модель.
- **CHECK `model_has_vector` и удаление.** Удаление по ФТ-13 обязано обнулять и `embedding_model`, иначе 23514;
  тест на это есть. Кода удаления в приложении пока нет (2.4) — в карточку 2.4 (MINOR-1).
- **Правки тестов A8.** Не ослаблены, а приведены к новому смыслу:
  - `test_auth_a8`: в список публичных путей добавлен `/help/contacts` **с проверкой** «без сессии — 200 и
    непустой список»;
  - `test_account_api_a8`: путь исключён из «всё 401 после удаления», но добавлена проверка «с токеном
    удалённого — 200 и есть 112»;
  - `test_chat_a8*` (A3): векторы помечаются моделью, удаление обнуляет модель, тест «косинус вне цикла» стал
    строже — расчёта в приложении нет (`not hasattr(rank_by_similarity)`), а старейшая, но ближайшая запись
    находится первой, то есть предела «200 свежих» больше нет;
  - `test_rls_a8`: новые функции внесены в списки;
  - strict-xfail `test_help_contacts_served_without_session` снят, потому что тест проходит.

## 3. Замечания

BLOCKER и MAJOR нет.

- [MINOR-1] migrations/versions/0008_vector_search.py (права 0001 не тронуты) — у `feelings_app` остаётся прямой
  `UPDATE` колонок `memory_items.embedding` и `embedding_model` своих строк. Проверено: `has_column_privilege` = t;
  у `feelings_admin` то же для `kb_chunks`. Значит, слой приложения может переписать имя модели у чужого по модели
  вектора или скопировать вектор другой строки в обход `app_set_memory_embedding` — и правило АР-5 «поиск только
  по векторам текущей модели» держится на коде, а не на БД. Обнулять (удаление ФТ-13) приложению нужно, ставить
  значения — нет. Ожидание: в миграции 2.4 — триггер «`embedding`/`embedding_model` меняются вне функции только на
  NULL» или column-level REVOKE и обнуление через функцию удаления. В карточку 2.4.
- [MINOR-2] backend/app/repositories/chat.py (`_memory`) — откат «на свежесть» есть только при отсутствии вектора
  или модели. Если `app_memory_nearest` упадёт (22023 при неожиданном векторе, отсутствие функции на
  непромигрированной БД, нехватка прав), ошибка оборвёт транзакцию `read_context`, и сборка контекста упадёт целиком
  (в API — `error` вместо ответа). Ожидание: вызов в `begin_nested()` (точка сохранения) с переходом на свежесть и
  отметкой `stats.embedding_error`; тест с 22023 из функции.
- [MINOR-3] 0008 `app_kb_nearest` — при фильтре по темам или уровню HNSW почти всегда даёт недобор, и запускается
  точный перебор всех фрагментов отобранных материалов. Сейчас база пуста, но при наполнении 2.6 (десятки тысяч
  фрагментов × 1024) это десятки–сотни миллисекунд на каждую реплику с фильтром. Ожидание: в 2.6 — замер на
  реальном объёме, при необходимости частичные индексы по подходу или pgvector ≥ 0.8 (iterative scan); записать
  в карточку 2.6.
- [MINOR-4] backend/app/api/chat.py:393 (`knowledge=rt.knowledge`) — `DbKnowledgeBase` в API не подключён (по
  умолчанию `None`; `rt.embedder` тоже `None`, поэтому в API нет поиска ни по памяти, ни по базе знаний). Объект
  нужен на каждый запрос (`user_id`, модель эмбеддера), а не на процесс. До 2.6 и до выбора модели эмбеддингов это
  допустимо; в карточку 2.6 — создание `DbKnowledgeBase(sm, user_id, embedder.model)` в `_prepare` и тест API.
- [MINOR-5] prompts/dialog.v0.md / dialog.v1.md, §6.4 — «пользователю текст книг не цитируется» обеспечен только
  запретом в промпте. Модель может пересказать или процитировать фрагмент близко к тексту, а это и §6.4, и вопрос
  прав на материалы. До наполнения (2.6) риска нет. Ожидание в 2.6:
  - проверка ответа в коде (общая подстрока с фрагментами длиннее N символов или доля совпадающих n-грамм → ответ
    переписывается или фрагмент снимается);
  - эталонные ситуации на «не цитировать»;
  - фрагменты во входе модели помечены как справочные и не для показа (уже есть в промпте, сохранить).
- [MINOR-6] 0008 `app_memory_nearest` — `count(*)` подходящих записей на каждый вызов перед выбором пути — лишний
  проход по индексу `agent_id`. Для объёмов одного агента это дёшево; если на 2.4 записей станет много, проверить
  `LIMIT 1001` вместо полного подсчёта.
