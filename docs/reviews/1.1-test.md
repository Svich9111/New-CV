## 4. Дефекты

- **[MAJOR] D-1** `backend/app/api/auth.py:29-35`, `backend/app/core/session.py:16-17` — при пустом
  (или < 32 символов) `FEELINGS_SESSION_SECRET` `issue_token` бросает `SessionError`, который не
  обрабатывается: ответ `500 text/plain "Internal Server Error"` (не схема Error контракта), а
  пользователь к этому моменту уже создан `upsert_by_telegram_id` (проверено: строка в `users`
  есть). Токен со слабым ключом не выдаётся — это хорошо. Ожидается: отказ в формате Error
  (например 503 `misconfigured`) без создания пользователя — проверка секрета до upsert, а лучше
  отказ старта приложения при пустом/коротком секрете вне `env=dev`/тестов (карточка: «При отказе
  пользователь в БД не создаётся», «Ответы — по контракту»). Тест:
  `test_empty_session_secret_controlled_refusal` (xfail).
- **[MINOR] D-2** `backend/app/core/session.py:24-35` — `read_token` не проверяет длину секрета,
  в отличие от `issue_token`: при секрете < 32 символов принимаются токены, подписанные этим
  ключом (подбор перебором). Пустой секрет отсекает только PyJWT (`InvalidKeyError`), а не код
  проекта. Ожидается симметричный отказ (или отказ при старте). Тест:
  `test_weak_session_secret_rejects_tokens` (xfail).
- **[MINOR] D-3** `api/openapi.yaml` `/auth/telegram` объявляет только 200 и 401, а код
  возвращает ещё 403 `account_deleted` (`auth.py:31`) и 422 `validation_error` (пустой или
  > 8192 символов `init_data`). Формат тела — Error, но коды не в контракте. Ожидается: A1
  добавляет 403/422 в контракт (через карточку) или код приводится к 401.
- **[MINOR] D-4** Тестовый пробел у исполнителя: удаление проверки дубликатов ключей
  (`telegram.py:51`) не ловится `test_telegram_init_data.py` (мутация M5). Закрыто тестом A8.
- **[MINOR] D-5** `uv run mypy .` падает на `tests/test_contract.py` (нет `types-PyYAML`); в
  `make lint` проверяется только `app`. `jsonschema`/`referencing`, используемые в тесте A8, —
  транзитивные зависимости `openapi-spec-validator`, а не прямые в `dev`-группе. Не блокирует.

## 5. Итог

Проверка подписи initData корректна и устойчива к реальным особенностям Telegram (поле
`signature`, unicode, порядок полей, `+`/`%20`, регистр hash), гонка первого входа обрабатывается,
имя не сохраняется, в журналах нет initData и токена. Не выполнен критерий «при отказе
пользователь не создаётся / ответы по контракту» в случае неверной конфигурации секрета сессии
(D-1, MAJOR).
