## 2. Находки

**[MAJOR-1]** `backend/app/workers/notify.py:341-371` — процесс не обрабатывает SIGTERM/SIGINT: `_main` вызывает
`run_forever()` без `stop`, сигнальных обработчиков нет. На `docker stop` / `dc up -d` с пересозданием
контейнера Python завершается сразу (действие SIGTERM по умолчанию), код «дожидаемся начатых»
(`:331-334`) в продукте недостижим. Уведомление, чей `sendMessage` уже дошёл до Telegram, но отметка
`pipeline_notify_done` не записана, после истечения аренды уйдёт второй раз — на каждой выкладке и
перезапуске сервера; запрос, прерванный посреди отправки, тоже повторится (обход `maybe_sent`).
Это нарушает критерий «Ровно одно уведомление на сообщение: … падение, повторы» и отличается от
бота (`bot/poll.py:218`, тесты `test_poll_real_sigterm_…` в 1.4). — Ожидание: обработчик SIGTERM/SIGINT
через `loop.add_signal_handler` → `stop.set()`; после остановки новые захваты прекращаются, начатые
отправки не повторяются (текущий запрос дорабатывается и отмечается; повторы внутри аренды при
остановке — не начинать); `stop_grace_period` у `worker-notify` в обоих compose не меньше тайм-аута
запроса Bot API + отметки (сейчас по умолчанию 10 с = `DEFAULT_TIMEOUT` чтения, `client.py:26`);
тест с настоящим `os.kill(SIGTERM)` по образцу 1.4: идёт отправка → сигнал → одно уведомление,
отметка стоит, процесс вышел с кодом 0. (Карточка 3.5, критерий 3; ТЗ §4.4 п.3.)
Замечание вне 3.5: у `workers/pipeline.py:443-472` то же самое — предложить в BACKLOG.

**[MINOR-1]** `backend/app/workers/notify.py:269-271, 32-35` — ошибка настройки (401/404) и 429 дольше окна
расходуют попытки: пауза 5 мин > аренды 2 мин, каждый захват после паузы — новая попытка, и через
≈ `max_attempts` пауз (≈ 25 мин неверного токена) все накопившиеся уведомления помечаются БД как
сделанные без отправки — без следа, кроме ERROR-строк «paused». Документировано в модуле, предложение
A1 `pipeline_notify_release` есть, но не заведено. — Ожидание: запись в BACKLOG/DECISIONS (остаточный
риск, как АР-45) и строка в `docs/DEPLOY.md` §4 «Причины сбоев» о том, что при неверном токене
уведомления теряются через ~N минут; либо функция снятия аренды без расхода попытки (A1).

**[MINOR-2]** `backend/app/workers/notify.py:230-242` — `asyncio.timeout(left)` охватывает и поиск чата в БД
(`users.notification_chat_id`), и HTTP-запрос. Если срок истёк во время поиска чата (медленная БД),
исход — `unknown`/`deadline` с отметкой, хотя запрос к Telegram не отправлялся: уведомление теряется
без причины. — Ожидание: различать фазу (истечение до начала `sendMessage` → `_Leave("retry")`), либо
искать чат до входа в `asyncio.timeout`; тест на истечение срока посреди запроса (сейчас ветка
`deadline` тестами не покрыта).

**[MINOR-3]** `docs/DECISIONS.md` — не записаны решения, которые карточка оставила на выбор/обсуждение и
