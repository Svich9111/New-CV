### Находки

- **[MAJOR] `backend/tests/test_worker_health.py:273` и `:596`.** `test_rejected_worker_login_is_config_error_not_retry`
  и `test_process_rejected_db_login_exits_78` молча предполагают, что кластер проверяет пароль. На
  стандартном облачном кластере 5432 вход `trust` (так указано в CLAUDE.md), поэтому неверный пароль принимается. Воркер
  работает штатно, и тесты падают по тайм-ауту: первый через `wait_for(…, 20)` → `TimeoutError`,
  второй через `subprocess.run(timeout=60)` → `TimeoutExpired`. Значит, полный `make test` в
  документированном окружении красный, а тест ещё и запускает реальный цикл захвата (`run_forever`) на
  общей БД.
  **Ожидание:** перед тестами проверить способ входа (подключиться с заведомо неверным
  паролем). Если подключение прошло, `pytest.skip("кластер без проверки пароля (trust): отказ входа
  не проверить — нужен scram, см. CLAUDE.md")`. В CI, где `CI=true` и есть контейнер с
  `POSTGRES_PASSWORD`, то есть scram, такой пропуск должен быть ошибкой (`pytest.fail`), иначе тест незаметно перестанет
  работать. Случай «нет базы» (3D000) от способа входа не зависит, его вынести отдельно и не
  пропускать. CLAUDE.md: «не отмечает задачу готовой при красных тестах».

- **[MINOR-1] `backend/app/workers/memory.py:80-123`, `backend/app/workers/kb.py:81-101`.** После SIGTERM
  `run_once` всё равно доделывает захваченную пачку. В воркере памяти он после этого ещё и
  **захватывает новую работу** (`claim_compaction`, `memory.py:104`), хотя `stop` уже выставлен. У
  memory/kb нет `stop_grace_period`, Docker убивает их через 10 с, начатый вызов модели
  оплачен впустую, аренда держится до истечения. ADMIN §4 обещает «новое не захватывается».
  **Ожидание:** передать `stop` в `run_once`, проверять его перед каждым захватом и между задачами
  пачки; добавить тест «stop между extraction и compaction — compaction не захвачен».

- **[MINOR-2] `backend/app/workers/notify.py:211-218, 372-376`; `backend/app/workers/pipeline.py:264-269`.**
  Состояние `paused` живёт только `cfg.pause` (5 мин). Если очередь пуста, следующего 401/404
  (или `auth`/`quota` у модели) не будет, и пульс вернётся в `ok`: при неверном токене бота
  контейнер станет `healthy`. В DEPLOY §4 написано, что неверный токен виден как `unhealthy`. **Ожидание:** либо при
  старте notify проверять токен (`getMe`; 401/404 → ConfigError → код 78), либо держать
  `paused` до первой успешной отправки. Как минимум описать в DEPLOY §4, что состояние отражает
  последнюю замеченную ошибку.

- **[MINOR-3] `backend/app/workers/pipeline.py:457`, `backend/app/workers/notify.py:441`.** Когда все слоты
  заняты, пульс `ok` идёт безусловно. Если начатая задача зависла вне своих тайм-аутов (например,
  запрос к БД без `statement_timeout` в записи исхода), health check останется зелёным.
  Сейчас задачи ограничены окнами аренды, поэтому риск низкий. **Ожидание:** при занятых слотах
  писать `ok`, только если хотя бы одна задача моложе аренды (или по возрасту самой старой),
  либо записать этот риск в docstring модуля `health.py`.

- **[MINOR-4] `backend/tests/test_worker_health.py`.** Нет теста «у notify пульс не обновляется, когда
  захват падает» (для pipeline и memory такие тесты есть) и нет теста SIGTERM для memory/kb
  (`_main` помечен `pragma: no cover`). **Ожидание:** добавить тест для notify. SIGTERM memory/kb
  проверить вместе с MINOR-1.

- **[MINOR-5] `backend/app/workers/health.py:134`.** Метка из будущего (отрицательный возраст) считается свежей,
  проверки `age < 0` нет. Часы в контейнере общие, так что риск ничтожный, но строка
  `age=-…s` в журнале запутает. **Ожидание:** при `age < -5` считать пульс неисправным
  (`unhealthy`).

Проверено, замечаний нет:
- В файл пульса попадают только `ts`, `state` и код причины.
- Запись атомарная. Сбой записи один раз пишется в журнал без пути.
- Строка CRITICAL при коде 78 печатается без трассировки, без значений и без адреса БД (`raise … from None`).
  Проверено тестами `test_process_*_exits_78` (на 5433).
- SQLSTATE 42501 считается ошибкой настройки только на захвате: задачи обёрнуты в `_guard`, их
  42501 (`gone`) до `run_forever` не доходит.
- При коде 78 из цикла pipeline/notify `finally` дожидается начатых задач.
- kb без ключа или с отклонённым ключом работает без меток, как и раньше.
- В `startup_retry` остановка прерывает ожидание. Пауза растёт до 60 с.

**Условие приёмки A:** АР-49 подтверждает оператор (restart-политика, grace 200 с). Пока
статус «Предложено», задачу нельзя считать готовой.

### Помощник захвата `tests/_pipeline_helpers.py`

- Чужие строки не крадутся. Удержание `FOR UPDATE SKIP LOCKED` (`:34-36`) конфликтует с

  Завершение `couple_ended`/`attempts_exhausted` трогает только строки, которые сам захват

  `delivered`, на этом упадёт.
