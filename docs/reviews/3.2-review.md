**MAJOR-2** `backend/app/workers/pipeline.py:173–176` — `quota`/`auth`/`config`/`bad_request`/`model_not_found` →
сразу `withheld/pipeline_error`, одобрение израсходовано, автору нужно новое «Отправить». Буквально это следует
АР-27 («ошибки настройки — не доставляется»), но АР-27 решает, *что не доставлять без адаптации*, а не что сообщение
нужно окончательно закрыть. Последствие: при исчерпании кредитов (текущее состояние, см. «Ограничения» карточки),
отозванном ключе или опечатке в id модели **все** сообщения всех пар за время инцидента безвозвратно становятся
«не доставлено», хотя после пополнения/исправления они прошли бы. Это противоречит §10 («отказ модели —
понятное сообщение, черновик не теряется»; черновик уже `sent`, повторно его не отправить) и превращает
эксплуатационный инцидент в потерю сообщений у пользователей. Тест `test_config_error_is_pipeline_error`
закрепляет именно это поведение.
Предложение (нужна запись в `DECISIONS.md`):
- `quota`, `auth`, `config`, `model_not_found` — «сервис не настроен», а не свойство сообщения: не завершать и не
  расходовать попытку; воркер переходит в паузу (circuit breaker: перестаёт захватывать на N минут, пишет ERROR
  без текстов — сигнал мониторингу), сообщение снова в очереди. Для этого A1 — функция
  `pipeline_release(p_message, p_token, p_retry_after interval, p_count_attempt boolean)` (снять аренду досрочно и
  при необходимости вернуть счётчик). Предел ожидания — по возрасту (`sent_at` старше, напр., 24 ч →
  `attempts_exhausted`), чтобы автор не видел «отправляется» бесконечно;
- `bad_request` (ошибка в коде, детерминирована для этого запроса) — оставить `pipeline_error`;
- в любом случае автору в `pipeline_error`/`attempts_exhausted` клиент должен предлагать «отправить снова»
  (новый черновик с тем же текстом) — передать в 3.4.
