## 5. Дефекты

- **[MAJOR] D-1 (для A1)** `api/openapi.yaml:134-213` — сервер отдаёт статусы, которых нет в
  контракте. Критерий 3 требует «ответы строго по контракту», задача 0.7 — «каждый фактический
  статус объявлен». Что именно не объявлено:
  - 401 `unauthorized` — на всех шести путях пары;
  - 403 `onboarding_required` — на `GET /couple` и `POST /couple/leave`;
  - 404 `not_found` — на `POST /couple/invite` (нет пары, FB007);
  - 503 `service_unavailable` — на `POST /couple` и `POST /couple/invite` (нет имени бота).

  Ожидается: A1 добавляет `"401": Unauthorized`, `"403": OnboardingRequired`, `"404": NotFound`,
  `"503"` в ответы этих путей. Отдавать ли 503 вообще, решают A1 и A2: при штатном запуске он
  недостижим, сервис без имени бота не стартует. Пути пары нужно внести и в `SERVED_STATUSES`
  в `test_contract.py` (совпадает с 1.3-review MAJOR-1).
  Тесты: `test_couple_api_a8.py::test_served_status_is_declared[…]` — 11 `xfail(strict=True)`.
- **[MINOR] D-2 (для A2)** `backend/app/errors.py` — нет обработчика `StarletteHTTPException`.
  `GET /api/v1/invites/`, `/invites/aaaa%2Fbbbb` и `/invites/a/b/accept` получают 404
  `{"detail": "Not Found"}` не по схеме `Error`. Тело отличается от ответа на несуществующий
  токен, и по нему видно «неверный формат» (критерий 3; ТЗ §9.1). Утечки существования нет:
  символа «/» в base64url не бывает. Ожидается единый `{code: not_found, message}` для
  ненайденных маршрутов (и `405` по схеме `Error`).
  Тесты: `test_token_with_slash_answers_like_missing[*]` — 3 `xfail(strict=True)`.
- **[MINOR] D-3 (вопрос для A0, оформить в DECISIONS)** `backend/app/api/couple.py`:
  `leave_couple` объявлен с `OnboardedUser`. После ответа «мне нет 18» (`PUT /me/onboarding`,
  `age_confirmed=false`) человек не может выйти из пары по HTTP (403), хотя:
  - `app_leave_couple` по АР-13 намеренно не требует онбординга (выход после отзыва 18+ проверяет
    `test_couple_functions_a8.py`);
  - ТЗ §4.5 п.2 говорит: «любой из партнёров может выйти».

  Пара при этом остаётся `active`, партнёр продолжает её видеть. Карточка (критерий 2: «все
  эндпоинты требуют `OnboardedUser`») реализацией соблюдена, поэтому это расхождение карточки
  и API с АР-13, а не ошибка исполнителя. Обходной путь есть: повторное «да» (АР-14) возвращает

### Замечания A2 к раунду 2: оценка A8

- **`method_not_allowed` нет в `Error.code.examples`.** Схеме код соответствует: `examples` — не `enum`. Но правило задачи 0.7 и D-4 — «каждый отдаваемый код перечислен». То же относится к запасному `http_error`, который сейчас недостижим. Оценка — MINOR, в бэклог для A1 (R2-2). 1.3 не блокирует: 405 возникает только при ошибке клиента и к сценариям ФТ-03/ФТ-04 не относится.
- **500 не объявлен.** При непредвиденной ошибке БД (коллизия хеша токена, вероятность ≈2⁻²⁵⁶) Starlette отдаёт `text/plain` `Internal Server Error`, а не `Error`. Это общий вопрос для всех эндпоинтов, а не только для 1.3. Тело ничего не раскрывает: ни токена, ни SQL (проверено тестом). Оценка — MINOR, в бэклог (R2-3): общий обработчик `Exception` → 500 `{code: internal_error}`, плюс `responses/InternalError` в контракте (A1, A2). Отказ «только объявленные статусы» в `test_served_status_is_declared` это не нарушает: 500 там не заявлен как отдаваемый в штатных сценариях.

### Новые дефекты

- **[MINOR] R2-1 (для A2, в бэклог)** `app/errors.py`, `_http`. У пути с несколькими методами 405 несёт `Allow` только первого маршрута: `DELETE`/`OPTIONS`/`HEAD /couple` → `Allow: GET`, а должно быть `GET, POST`. Это особенность маршрутизатора Starlette: заголовок берётся из первого частично совпавшего маршрута. RFC 9110 §15.5.6 требует перечислить все методы ресурса. На продукт не влияет: Mini App ходит только объявленными методами. Тест — `test_405_allow_lists_all_methods_of_path`, `xfail(strict)`.

- **[MINOR] R2-3 (для A1/A2, в бэклог, общий)** 500 отдаётся `text/plain` не по схеме `Error` и в контракте не описан.
