## 3. Замечания

BLOCKER и MAJOR нет.

### MINOR

**[MINOR-N1] `backend/app/api/chat.py:824` — повтор (б) после кризиса, ответ на который не сохранился, пишет второй
`safety_events` на ту же реплику.**
В первой попытке `_record_crisis_now` записывает событие, а сохранить ответ протокола не удаётся
(`chat.py:661`, «crisis reply not saved»), либо клиент ушёл до сохранения. Реплика остаётся «без ответа». Повтор с тем
же ключом снова запускает классификатор и `_record_crisis_now`, и для одной реплики получается два события.
Ответ ничем не смягчается, контакты уходят, так что риска для человека нет. Но статистика кризисов (ФТ-17) завышается,
а это противоречит формулировке АР-51 «повтор… без второго события». Тест есть только для (а).
Ожидание: отметка «событие безопасности записано» у реплики (как `limit_charged`), или запись событий в (б) только
при её отсутствии. Можно и оставить, но тогда это допущение нужно записать в АР-51. Ссылки: АР-51, АР-34, ТЗ §9.3.

**[MINOR-N2] `backend/app/api/chat.py:347, 372` — аренда не снимается, если задача-производитель отменена до первого
шага.**
`release_lease` вызывается в `finally` метода `_Reply.produce`. `EventStreamResponse.__call__` создаёт задачу и сразу
шлёт `http.response.start`. Если запись заголовков падает (`OSError`) до того, как задача начала выполняться,
`_cancel_and_wait` отменяет её, корутина не стартует, и `finally` не выполняется. То же будет, если ответ вообще не
отправлен. Тогда аренда держится до истечения срока, 5 минут. Клиент три раза получит 409 «ещё готовится»
(3/6/10 с), затем «Повторить» и снова 409. Случай редкий: клиент должен отключиться ровно между возвратом ответа
и первой записью.
Ожидание: снимать аренду там, где создаётся ответ, а не внутри корутины. Например, в `finally` обёртки `run()`
внутри `EventStreamResponse` или через `BackgroundTask` ответа. Ссылки: АР-51 «снимается по завершении запроса
любым исходом».

**[MINOR-N3] `backend/tests/test_chat_idempotency.py` — нет теста на повтор (б) для реплики, которая уже вошла в
сводку.**
По коду результат верный (`error` `internal`, при кризисе по самой реплике — `crisis`), и для этого случая АР-51
оставляет вопрос 2 оператору. Но сейчас поведение держится на побочном эффекте: `ValueError` из `_turns` при пустом
хвосте. Также не проверено, что лимит за такую реплику засчитывается один раз (`acquire` идёт до потока, который
заведомо завершится `error`).
Ожидание: тест — сводка с отметкой позже X (как `summary_envelope` в `test_chat_a8.py`), повтор X даёт
`accepted(replayed)` + `error internal`, модель ответа не вызывается, второй повтор лимит не расходует. Ссылки: АР-51
(б), АР-32.

**[MINOR-N4] `frontend/src/chat/session.ts:31` — значения пауз 3/6/10 с тестами не закреплены.**
Все тесты 409 подменяют `replyWaitMs` (`[5, 5]`, `[60_000]`), а `REPLY_WAIT_MS` по умолчанию нигде не проверяется.
Если значения изменить или очистить массив, тесты не упадут. Логика пауз проверена хорошо: число автоповторов,
неизменный ключ, «Остановить» во время паузы, ответ, сохранённый пока ждали.
Ожидание: одна проверка `REPLY_WAIT_MS` (`[3000, 6000, 10000]`) или тест на поддельных таймерах с настройками по
умолчанию. Ссылка: карточка, критерий 409.

**[MINOR-N5] `frontend/src/screens/Chat.tsx:62`, блок лимита — у реплики со статусом «лимит» нет повтора, хотя сервер
по ключу ответил бы на неё после окна.**
Уведомление говорит «Твоё сообщение сохранено… Агент снова ответит …». По контракту АР-51 повтор с тем же ключом после
нового окна отвечает на ту же реплику. Но у статуса `limited` нет кнопки, и после окна человек может только написать
новую реплику, а сохранённая так и останется без ответа. Это не регресс, в р.1 было так же. Ожидание (на выбор A4):
кнопка «Повторить» после окна или уточнение текста: ответа на это сообщение не будет, после окна напиши снова.
Ссылки: ТЗ §10, АР-51.

## 4. Проверено, замечаний нет

- **Строгость `accepted` на клиенте** (`client.ts`). С ключом `accepted` должен прийти первым и один раз, с тем же
  ключом. `delta`/`done` до него дают `bad_response`. Кризис принимается и без `accepted`. Без ключа `accepted`
  пропускается.
- **Сверка по ключу.** Свои реплики без id находят запись по ключу. Ответ ищется только по `reply_to`. Свёртка
  одинаковых реплик осталась только для записей без ключа, до 0018.
- **409.** Сначала один немедленный повтор (`Api`), затем сверка. Реплики нет — «Не отправлено» с тем же ключом. Ответ
  есть — показан. Реплика без ответа — автоповторы через паузы, затем «Повторить».
- **422 под ключом.** Понятный текст, повтор с новым ключом.
- **Приватность.** Ключ генерируется клиентом (`randomUUID` или `getRandomValues`), хранится только в памяти. В адрес,
  хранилища и консоль не попадает.
- **Заглушка `fakeApi`** соответствует АР-51: повтор, аренда, 422, `ownerNotSaved`, `reply_to`/`crisis` у сохранённых
  ответов.
- **`schemas.py`.** `strict=False` снят только с `client_message_id`. Нестроковые и не-uuid значения дают 422
  (`test_key_must_be_uuid`).
- **История** (`get_messages`). Ключ отдаётся только у владельца, `reply_to`/`crisis` — только у агента, помимо CHECK
  в БД.
- **Правила `CLAUDE.md`.** SQL — только в `repositories/`. Промпты не менялись. Контракт изменён A1 по АР-51.
