## 2. Разбор решений A1

**Полнота удаления.** Все FK на `users` (0001): `agents`, `couple_members`, `invites.created_by`, `partner_messages.author_id`, `safety_events` удаляются каскадом (CASCADE); `invites.used_by`, `partner_messages.recipient_id`, `subscriptions.payer_id` обнуляются (SET NULL). `audit_log` без FK — его обнуляют явно. Таблиц, где после удаления остаётся id или текст удаляемого, я не нашёл. Остаются только производные данные у партнёра: `adapted_enc` и `tone_score` сообщений, адресованных удаляемому (MINOR-3), записи памяти партнёра типа `observation`/`agent_inference` (о них ниже) и статус `answered` у сообщений партнёра. Telegram ID удаляется вместе со строкой `users`. Хранилища вне БД (Redis, сессии бота) — дело этапа 2.

**Подписка и платежи пары без участников.** ТЗ о хранении платежей после удаления ничего не говорит. Само удаление допустимо по §4.5 п.3, но обоснование непоследовательно. Если в паре остался партнёр, платежи хранят «для учёта» (`0005:38-39`). Если пара опустела, те же платежи удаляют. При этом `provider_charge_id` нужен для возвратов и споров в Telegram Stars, а для учёта может действовать обязательный срок хранения. Это вопрос оператору, не A1 (MINOR-1).

**Обезличивание `audit_log`.** Выбор обоснован: после удаления id ни на что не указывает, а оставленный id был бы идентификатором на весь срок хранения журнала. Остаточная связь всё же есть: `couple.leave` с `object_id` пары и тем же `now()`, что у `account.delete`, плюс записи партнёра по этой же паре. По ним видно, что «бывший партнёр X удалил аккаунт». Партнёр это и так знает, отдельного замечания не завожу. Цена решения — восстановление из копии нельзя «доудалить» по журналу (MINOR-2).

**Память партнёра из сообщений удаляемого.** Принцип §2 п.6 гарантирует владельцу контроль над памятью. Он не запрещает удалять записи, которые являются данными другого человека. Запись `from_partner` — это цитата или вывод из сообщения удаляемого, то есть по §4.5 п.3 — «его данные». К тому же CHECK `ck_memory_items_partner_source_has_message` не даёт сохранить запись без источника. Решение согласуется с АР-23 и ТЗ. Наблюдения агента партнёра (`observation`) остаются: это вывод его агента из одобренных сообщений (§6.1 п.6), а ссылки на источник у них нет. Допустимо. Пояснение «из сообщений партнёра» на экране памяти (2.x) должно учитывать, что такие записи могут исчезнуть без действия владельца. Это пожелание к UI, не к этапу 1.

**`app_send_draft`.** Порядок блокировок: свой `users` (FOR KEY SHARE) → получатель (FOR KEY SHARE) → черновик (FOR UPDATE) → пара (KEY SHARE из FK вставки). Это совместимо с `app_delete_account` и `app_leave_couple` (пользователь FOR UPDATE → приглашения → пара). FOR KEY SHARE конфликтует с FOR UPDATE и не конфликтует с FOR NO KEY UPDATE при правке профиля. После ожиданий функция перечитывает пару и получателя и сравнивает получателя с заблокированным (`IS DISTINCT FROM v_locked`), так что подмена получателя исключена. Коды FA001…FA004 прежние, регрессии покрыты `test_rls_messages.py:261-296`. Новый 42501 для помеченного удалённым отправителя описан в АР-13, но не покрыт тестом (MINOR-4). Совместимость с 4.2 сохранена: в `original_enc` по-прежнему копируются байты `d.text_enc`, AAD черновика не меняется, тест `:816` расшифровывает оригинал после удаления. Получателя функция блокирует без условия `deleted_at IS NULL`. Поле больше не ставится, так что это несущественно.

**Права.** Если отозвать DELETE на `agents`, обычный сценарий ТЗ ничего не теряет: отдельного удаления агента в ТЗ нет. Политика `drafts_delete` без `sent` не мешает ни удалению неотправленного черновика, ни отказу «Не отправлять» (он идёт через `rejected` в `drafts_update` или через DELETE неотправленного черновика). Политика `users_update` при RETURNING опирается на `users_select` — проверено тестом `:446-449`.

## 3. Замечания

[MAJOR-1] backend/migrations/versions/0005_account_delete.py:128-143 (и описание `:20-26`, DECISIONS АР-23 «без взаимоблокировки с ним») — шаг 2 сначала блокирует сообщения партнёра, которые ссылаются на сообщения удаляемого, и только потом каскад удаляет сообщения самого удаляемого. Такой порядок совпадает с `pipeline_deliver` (ответ → исходное) лишь в одном случае: когда отвечает партнёр. Пробы A6 подтвердили две взаимоблокировки. (а) Удаляемый написал ответ Z, он ещё в `processing`, а Z отвечает на сообщение партнёра Y, которое само отвечает на сообщение удаляемого. `pipeline_deliver(Z)` берёт Z → Y, удаление берёт Y → Z. Итог — 40P01 (проба A6-2). (б) Оба бывших партнёра одновременно удаляют аккаунты после распада пары, а в истории есть встречные ответы. Сериализующей блокировки пары нет: `app_leave_couple` выходит с FB007 до `FOR UPDATE` пары. Каждый блокирует ответы другого, а затем ждёт их на каскаде. Итог — 40P01 (проба A6-1). Тест `test_race_both_partners_delete` (`test_account_delete.py:672`) проверяет только активную пару без переписки, поэтому случай (б) не ловит. Данные не портятся (транзакция откатывается), но пользователь или воркер получают ошибку, а документация утверждает обратное. — Ожидание: (1) в `app_delete_account` после шага 1 заблокировать пары из `v_couples` (`SELECT … FROM couples WHERE id = ANY(v_couples) ORDER BY id FOR UPDATE`), тогда удаления с общей парой сериализуются. (2) Для конвейера одно из двух: добавить в `pipeline_deliver`/`pipeline_withhold` первым шагом блокировку пары `FOR SHARE` (её ждёт `FOR UPDATE` удаления; это изменение затрагивает 3.2), или записать в АР-23 и карточку 3.2, что 40P01 и пропавшее сообщение для воркера — штатный исход с повтором или пропуском. (3) Исправить описание `0005:20-26` и АР-23. (4) Добавить тесты на оба сценария с детерминированным порядком через `_hold_and_race`. (Карточка: «Гонки … без взаимоблокировок, порядок блокировок как в АР-13».)

[MINOR-1] backend/migrations/versions/0005_account_delete.py:144-148, :34-39 — подписку и платежи опустевшей пары функция удаляет безвозвратно, а у пары с оставшимся партнёром хранит «для учёта». ТЗ этого не требует. Для учёта и возвратов Stars (`provider_charge_id`) могут действовать обязательные сроки хранения (152-ФЗ допускает хранение по требованию закона), а пары с одинаковой оплатой получают разную судьбу. — Ожидание: включить явный вопрос в подтверждение АР-23 оператором: хранить платежи обезличенно (например, отвязать от пары и пользователя) или удалять. До платёжной задачи достаточно записи в DECISIONS/BACKLOG (ТЗ §7, RoadMap §4 «платёжные настройки — после подтверждения оператора»).

[MINOR-2] backend/migrations/versions/0005_account_delete.py:149-151 (и АР-23) — §7 требует удалить данные «включая резервные копии». Восстановление ежедневной копии (§10, хранение 30 дней, проверка восстановления раз в квартал) вернёт удалённые аккаунты, а в журнале нет сведений, кого удалять повторно: `account.delete` без id. — Ожидание: в регламенте 4.7 или BACKLOG предусмотреть повторное применение удалений после восстановления (например, отдельный список удалённых id или хешей Telegram ID со сроком хранения 30 дней и очисткой) или записать в АР-23, что восстановление из копии, сделанной до удаления, недопустимо без такой процедуры.

[MINOR-3] backend/migrations/versions/0005_account_delete.py:29-33 — у сообщений партнёра удаляемому остаются `adapted_enc`, `tone_score`, `harsh_tone_warning`. ## 4. Безопасность, изоляция, CLAUDE.md

- Функция SECURITY DEFINER с `search_path = public, pg_temp` (тест `:469-484`). EXECUTE есть только у `feelings_app`, у `PUBLIC` отозван. Действует только на `app_uid()`, параметров нет, инъекции нет.

- Тексты в журнал не пишутся. `audit_log` после удаления не содержит id удаляемого (тест `:285`).
- Слой доступа и контракт диффом не затронуты. Эндпоинты — этап 2. Промптов нет.
- Миграция выполнялась только на локальной и тестовой БД (АР-4). Для продуктива нужно подтверждение оператора, особенно с учётом MINOR-1.
- Тесты не ослаблены. Красные тесты `test_rls_a8.py` отражают изменённую семантику (Б-19, Б-38, D-7), их обновляет A8. До закрытия задачи они должны быть зелёными.

### Новые проверки

**Пересоздание функций конвейера.** `pipeline_deliver` и `pipeline_withhold` в 0001–0004 менялись только в 0001.
В 0005 все проверки 0001 сохранены: `status = 'processing'`, `p_for_recipient IS NOT NULL`, переход исходного сообщения
в `answered` только из `delivered/read`, тот же результат `EXISTS (u)`. Сохранены также `LANGUAGE sql VOLATILE SECURITY DEFINER`,
`search_path = public, pg_temp` и сигнатуры. `CREATE OR REPLACE` сохраняет владельца и ACL: EXECUTE остаётся
только у `feelings_worker`, это проверяет `test_rls_a8.py::test_definer_functions_…`. Функция VOLATILE, поэтому каждая команда SQL-функции
получает новый снимок: после ожидания пары UPDATE видит удалённое сообщение (`false`), пару, удалённую как опустевшую, блокировка пропускает,
и UPDATE тоже не находит строки. `app_send_draft` в 0002–0004 не менялся, так что downgrade к определениям 0001 корректен.

**`pipeline_deliver` при `recipient_id IS NULL`.** `NULL` в `recipient_id` бывает только после удаления получателя:
`app_send_draft` всегда ставит получателя. Для такой строки доставка ставит `delivered` без версии для получателя.
CASE берёт значение старой строки, и это правильно. CHECK `adapted_has_text` выполняется. При живом получателе поведение прежнее,
это проверяет тот же тест на третьем сообщении (Ольга). Регрессии для 3.2 нет. Требование `p_for_recipient IS NOT NULL` осталось,
поэтому воркер должен передать какую-то версию и для удалённого получателя. Это попадает в Б-44, отдельного замечания нет.

**Порядок блокировок.** Перебрал пары транзакций: удаление и удаление, удаление и выход, принятие приглашения, отправка,
`pipeline_deliver`/`withhold`, `app_mark_read`, `create_draft` с ответом. Удаление сначала берёт активную пару внутри `app_leave_couple`,
потом все пары по id. Цикла здесь нет: если чужая активная пара входит в набор другого удаляемого, у них общая активная пара,
и они встречаются уже на `app_leave_couple`. `FOR KEY SHARE` пары в конвейере совместима с вставкой сообщения (KEY SHARE из FK)
и с `FOR NO KEY UPDATE` (будущие изменения подписки 4.4). Ждёт её только `FOR UPDATE` (удаление, выход, принятие).
Новых циклов в однострочных транзакциях конвейера не нашёл.

**`audit_insert` с `FOR KEY SHARE`.** Подзапрос с блокировкой в политике требует права UPDATE на `users` и прохождения `users_update`;
у `feelings_app` и то и другое есть. Если запись в журнал идёт параллельно с удалением, взаимоблокировки нет:
`app_delete_account` до строки пользователя ничего не держит. 40P01 возможен только при повышении блокировки:
две транзакции одного пользователя сначала пишут аудит от его имени, затем обе берут его строку `FOR UPDATE`
(удаление, функции пары). Проба это подтвердила. Сейчас приложение `audit_log` напрямую не пишет: журнал ведут только функции SECURITY DEFINER
от владельца таблицы, и политика на них не действует. Поэтому сценарий пока недостижим, а позже — редкий и безопасный
(откат, данные целы). Цену считаю приемлемой при условии MINOR-9.

### Разбор по пунктам постановки

1. **Изоляция.** Каждый раздел читается под RLS в `user_scope` и дополнительно отбирается по владельцу. У полученных
   `draft_id` используется только как AAD, в модель не попадает: в `ExportReceivedMessage` такого поля нет, а `extra=forbid`
   не даст его добавить незаметно. `adapted_enc` своих отправленных функция возвращает как NULL (`shown_enc`). Это
   проверено и сигнатурой функции (`test_execute_only_for_app_role`), и поиском метки. Контекст ИИ не затронут:
   новых чтений в сборке контекста нет. Утечек не нашёл.
2. **Контракт.** Состав полей схем и Pydantic-моделей совпадает. `assert_matches(…, "AccountExport")` выполняется на каждом
   ответе выгрузки, `no-store` проверен.
3. **SQL и журналы.** Весь SQL — в `repositories/account.py`, `users.py` и миграциях. Обработчики только вызывают слой доступа.
   В журнал выгрузки попадают только `field=table.column reason=…`, это проверено тестом с поиском id и меток.
4. **Фиксация просмотра при сбое расшифровки** — см. MINOR-2.
5. **Общий обработчик `DBAPIError`.** Он ловит только `sqlstate ∈ {40P01, 40001}`, остальное перебрасывает (стандартный
   путь 500). В ответе фиксированный код и текст, без SQL, параметров и `orig`. 40P01/40001 отменяют транзакцию целиком;
   `user_scope` откатывает её при выходе, поэтому повтор `DELETE /me` и выгрузки безопасен: каждый — одна транзакция.
   Утверждение контракта «на любом эндпоинте… ничего не изменено» держится, только пока каждая запись — одна транзакция
   (MINOR-4).
6. **401 после удаления.** `current_user_id` проверяет строку при каждом запросе. Токен удалённого (и токен старого id после
   повторной регистрации) — 401. Гонка «проверка прошла, пользователь удалён до вызова» → 42501 → `AccountGone` → 401
   (`test_delete_and_export_of_vanished_user_is_401`).
7. **Функции 0006/0007.** Обе SECURITY DEFINER, `search_path = public, pg_temp`, имена квалифицированы. Права:
   `REVOKE ALL FROM PUBLIC` и `EXECUTE` только `feelings_app` (проверено тестами для worker/admin/api/public). При
   `app_uid()` NULL, неизвестном или `deleted_at` — 42501. 0006 VOLATILE обязательно: в ней UPDATE. Пустой
   `RETURNING` в CTE и `COALESCE(v.…, m.…)` корректно дают значение после фиксации в одном снимке. Порядок блокировок:
   пользователь `FOR KEY SHARE` → текущая пара → все пары по id → полученные `FOR UPDATE ORDER BY id`. Он совпадает с
   `app_delete_account`, а общие пары двух пользователей берутся в одном порядке. Строка, ставшая `delivered` между
   PERFORM и UPDATE, блокируется самим UPDATE; держатель её блокировки (доставка) не ждёт выгрузку, поэтому цикла нет.
   0007 STABLE корректна: только чтение. Строка пользователя к этому моменту уже под `FOR KEY SHARE` от 0006 в той же
   транзакции, так что проверка `deleted_at` без блокировки достаточна.
8. **`notify_user`.** Чат берётся в момент отправки в области самого получателя: RLS открывает только свою строку.
   Удалённый или неизвестный получатель → `False`, без журнала. После повторной регистрации того же Telegram ID старый id
   не найдётся, так что новый пользователь чужих уведомлений не получит. Окно «прочитали chat_id → пользователь удалился
   → отправили» допустимо. Замечание — MINOR-3.

42501. Этот SQLSTATE не только «нет пользователя» из функций, но и `insufficient_privilege`: «permission denied for
table/column/function». Если права слетят (отозван EXECUTE на `app_export_*`, не выдан SELECT на новую колонку,
ошибка будущей миграции), выгрузка и удаление ответят 401: клиент разлогинит пользователя, а сбой конфигурации
маскируется вместо 500. В `couples._db_errors` 42501 тоже попадает в известные коды, но там это сделано по ранее
принятому решению. — Ожидание: различать «нет пользователя» (например, своим SQLSTATE класса FB или проверкой
`exc.orig`-сообщения/`users.is_active` до перевода) или хотя бы для выгрузки переводить в 401 только 42501 от
функций `app_export_*`. Добавить тест: отозванный EXECUTE → не 401 (ТЗ §12 п.7; карточка «не 500» относится к
40P01/40001, а не к маскировке прав).

[MINOR-2] backend/app/repositories/account.py:12-14, backend/tests/test_account_api.py:558-559, 619 — проблема: при
нерасшифрованном оригинале (`UnavailableText`) отметка `original_viewed_at` всё равно сохраняется. Это обратно семантике
`read_original` (`repositories/texts.py:415-416`: «просмотр засчитывается, только когда текст показан (ТЗ §7)»). По ТЗ §7
фиксируется выдача оригинала, а здесь ничего не выдано. Решение помечено как «решение A2» только в docstring и тесте,
в `DECISIONS.md` его нет. Колонка `original_viewed_at` автору доступна по SELECT (0001, грант на колонку): если
интерфейс когда-нибудь покажет автору «оригинал открыт», это будет ложный факт. — Ожидание: либо дописать подслучай в
АР-25 п.2 (он и так на подтверждении оператора) с явной ссылкой на расхождение с `read_original`, либо не засчитывать
выдачу нерасшифрованного оригинала. Вариант: второй функцией после расшифровки или параметром со списком успешно
расшифрованных id; тогда ответ `original_viewed_at` должен стать nullable в контракте (меняет A1). Без записи в
DECISIONS задачу не закрывать (CLAUDE.md: «отступление… только через запись в DECISIONS.md»).

[MINOR-3] backend/app/bot/notifications.py:29-47 — проблема: у `notify_user` нет ни одного вызывающего. Публичная
`notify(api, chat_id, …)` остаётся, и будущий отправитель уведомлений (3.x: «новое сообщение», «партнёр в паре») может
положить в очередь `chat_id` и обойти проверку. Критерий карточки «после удаления не шлёт» выполнен только для тех,
кто воспользуется `notify_user`. — Ожидание: в BACKLOG (или карточке 3.x) закрепить правило: очередь уведомлений хранит
`user_id`, отправка — только через `notify_user`; `notify` по `chat_id` — только для ответа на апдейт от самого
пользователя. По желанию — переименовать `notify` во внутреннюю (карточка 4.5 этап 2, критерий «Бот»).
