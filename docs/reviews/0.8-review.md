## Замечания

### MAJOR

**MAJOR-1** `infra/deploy/restore-check.sh:34`, `docs/DEPLOY.md:277-281`, `infra/db/init-owner.sql:64` —
`pg_dump -Fc` без `--create` не переносит права и настройки уровня базы. Миграция 0001 делает
`REVOKE TEMPORARY ON DATABASE … FROM PUBLIC` (АР-10: временные таблицы запрещены всем), а при
восстановлении в новую базу (`CREATE DATABASE … OWNER feelings_owner` в `restore-check.sh` и порядок
«`dc up postgres` → `db-init` → `pg_restore` → `db-roles`» в DEPLOY §10) этот отзыв пропадает.
Проверено: после восстановления `SET ROLE feelings_api; CREATE TEMP TABLE` проходит. `restore-check.sh`
это не ловит: он проверяет `alembic_version`, vector и RLS, но не права базы. В DEPLOY §10 для
восстановления нет команд, а сценарий «восстановить на том же сервере» (на него ссылается §7,
«если downgrade невозможен») не описан вовсе.
Ожидание: `init-owner.sql` идемпотентно отзывает у PUBLIC `TEMPORARY` (и при необходимости `CREATE`)
на базе. Тогда новый сервер и временная база проверки защищены. `restore-check.sh` проверяет права
базы (`has_database_privilege('feelings_api', db, 'TEMP') = false`) и EXECUTE функций vector у PUBLIC.
В DEPLOY §10 нужны точные команды восстановления для обоих сценариев (новый сервер, тот же сервер),
с подтверждением оператора (ТЗ §10, АР-10).

**MAJOR-2** `infra/db/init-owner.sql` (весь файл), `backend/tests/` — у нового привилегированного
скрипта, который выполняется суперпользователем, нет ни одного автотеста. Не покрыт и путь «миграции
под `feelings_owner`»: conftest мигрирует под суперпользователем, а АР-41 сам называет это открытым

которая не проходит под owner, тесты не заметят.
Ожидание: тест, как `test_login_roles_a8.py`, но для `init-owner.sql`. Варианты: имя владельца
параметром psql, чтобы не трогать общую роль (CLAUDE.md: роли `feelings_*` — только в откатываемых
транзакциях), либо отдельная задача CI с одноразовым кластером. Проверить: атрибуты, ACL функций
vector, пароль не в журнале при `log_statement=all`, `alembic upgrade head` → `downgrade base` →
`upgrade head` под owner, совпадение ACL с прогоном под суперпользователем (АР-41 «Проверено»).

**MINOR-1** `infra/deploy/Caddyfile:4-5` — утверждение «журнал доступа не ведётся, поэтому токен
приглашения не попадает в журнал» неполное. Журнал ошибок Caddy (`http.log.error`) при ответах 5xx

поднимался), поэтому нужно проверить на стенде: остановить api и отправить запрос на вебхук. Ожидание:
проверить и при подтверждении отфильтровать (`log` с фильтрами `request>uri`,
`request>headers>X-Telegram-Bot-Api-Secret-Token` для логгера ошибок или понизить его уровень);
поправить комментарий.

### Примечание (не замечание к 0.8)

Литерал без типмодификатора `'[1,2]'::vector` под `feelings_app` выполняется: функции ввода типа не
проверяют EXECUTE. При этом `::vector(1024)`, `text::vector` и `real[]::vector` дают «permission
denied». Так же ведёт себя база, мигрированная суперпользователем (`feelings_test`), так что
регрессии 0.8 нет. Формулировка АР-35 «приведение к vector закрыто» верна для приведения к
`vector(1024)` и функций. Передаю A1 для сведения.
