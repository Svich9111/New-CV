## 2. Ответы на особые вопросы

1. **Изоляция.** Путей к памяти, чату, агенту и профилю партнёра не нашёл: каждый запрос внутри `user_scope` и
   дополнительно с отбором по `agents.user_id = :u`; сообщения пары — через `app_couple_feed` (SECURITY DEFINER,
   `app_uid()`) с фильтром по текущей активной паре (`cm.active AND c.status = 'active'`) — бывший партнёр отсечён;
   `processing`/`withheld` отсечены и для своих, и для полученных; удалённая память — `deleted_at IS NULL`.
   Имя партнёра — из онбординга владельца. Тест с метками партнёра, бывшего и постороннего (их память содержит те же
   слова «деньги отпуск», поэтому поиск по смыслу был бы пойман) — корректный.
2. **§6.1 порядок и бюджет.** Порядок соответствует; системный промпт в `fit` не участвует, последняя реплика
   (обязательно владельца, `_turns` бросает `ValueError` иначе) не удаляется, только обрезается до `turn_chars`
   (= лимиту контракта 4000). При невозможности уложиться — `over_budget`, вход уходит как есть (задокументировано).
3. **Поток.** Придержка до вердикта ≤ `gate_timeout_s` реализована верно; `Done` не отдаётся до вердикта;
   при кризисе от классификатора ответ агента отбрасывается и в сохраняемый текст не попадает. Но после 3 с
   придержки куски агента уже видны пользователю, и замена держится на `replaces_streamed`, которого нет в контракте
   (MAJOR-3). Резерв — только до первого куска (`FallbackProvider.stream_text`), отказ на резерв не уходит (АР-20).
   `aclose` отменяет задачи (тест есть); замечание по `_cancel` — MINOR-1.
4. **Сжатие.** Конверт `{"v":1,text,through_at,through_id}` шифруется целиком (`CONVERSATION_SUMMARY`, AAD — id
   диалога), в БД ни текста, ни отметки; конфликт — `FOR UPDATE` + сверка `through_id`. Б-53 — MINOR-8.
5. **Косинус в приложении.** Корректен (фильтр удалённых, одинаковая размерность, добор по свежести), но не
   масштабируется — MAJOR-4.
6. **Стражи `OwnerContext`** (`test_ai_dialog.py:183`, `test_ai_pipeline_a8.py:662`): правка аддитивная — точное
   множество полей расширено двумя полями владельца, полей партнёра не добавлено, проверка не ослаблена; вход
   эталонного набора не меняется (пустые сводки не передаются). Приемлемо; A8 стоит об этом знать (страж его).
7. **Выгрузка.** Не сломана: `_summary` снимает конверт только у строки, `UnavailableText` проходит как есть,
   старая сводка без конверта выводится текстом.

## 3. Замечания

### MAJOR

- [MAJOR-1] backend/app/ai/context.py:58 (`recent_turns = 30`) и backend/app/ai/summary.py:39-41
  (`trigger_turns = 40`, `keep_turns = 12`) — после сжатия реплик снова набирается до 40, а в контекст идут только
  последние 30 (`LIMIT` в `repositories/chat.py:196-199`); реплики 31…40 после отметки не попадают ни в сводку, ни в
  контекст, а при сбоях модели сжатия (сейчас кредитов нет) «провал» постоянный. Агент «забывает» середину разговора —
  ожидание: §6.1 п.5 «последние реплики **и** краткое содержание предыдущих» без разрыва; согласовать пределы
  (`trigger_turns ≤ recent_turns`) и/или сжимать по бюджету контекста, с тестом на отсутствие разрыва.
- [MAJOR-2] backend/app/ai/summary.py:124-139 — `read_history` берёт **все** реплики после отметки
  (`limit=None`), и `old` целиком уходит в модель. После долгого периода сбоев сжатия пачка растёт без предела, вход
  превышает окно модели, сжатие падает каждый раз и уже не восстанавливается. Ожидание: ограничить пачку
  (самые старые N реплик / M символов за раунд, отметка — последняя вошедшая), тест на большой хвост
  (карточка: «сжатие истории при превышении»; §10 «отказ модели — понятное поведение»).
- [MAJOR-3] backend/app/ai/chat.py:18-22, 95, 296, 404-414 — параллельный режим показывает куски агента после 3 с
  придержки, а при позднем кризисе рассчитывает, что клиент заменит текст по `replaces_streamed`. В контракте
  (`api/openapi.yaml:294-298`) событие `crisis` — `{contacts}`, признака замены и итогового текста нет; там же порядок
  «сначала классификатор, потом лимиты». То же для `error` после показанных `delta`. Пока контракт этого не выражает,
  смягчённый ответ агента при кризисе остаётся на экране (§9.3 «ничего не смягчать», принцип 7). Ожидание: либо
  этап 2 использует только режим `screen()` → `stream_reply(safety=…)` и параллельный режим не включается по
  умолчанию (зафиксировать в карточке/коде), либо предложение A1 через карточку на поле замены в `crisis`/`error`
  (CLAUDE.md: контракт меняет только A1).
- [MAJOR-4] backend/app/repositories/chat.py:266-280, 369 — на каждую реплику читаются до 500 векторов текстом
  pgvector и считаются в Python в цикле событий. Замер на 500×1024: ≈ 0,2 с CPU и ≈ 5–10 МБ текста на один запрос —
  при «до 500 одновременных диалогов» (§10) это блокирует цикл событий и съедает бюджет «первый символ ≤ 5 с»; записи
  старше 500-й по смыслу не ищутся. Переход на `<=>`/индекс упомянут только как «отчёт 2.1», а отчёта A3 и записи в
  BACKLOG нет. Ожидание: запись в BACKLOG с владельцем A1 и сроком «до 2.4/Г3» (функция поиска SECURITY DEFINER или
  EXECUTE на операторы pgvector), до этого — расчёт вне цикла событий (`asyncio.to_thread`) или меньший предел.
