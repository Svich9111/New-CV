## 5. Дефекты и замечания

- **A8-4.4-D4** — закрыт (§2).
- **[MINOR] A8-4.4-D5** — `backend/migrations/billing_guard.py`, `_GRANTS`, ветка `pg_proc`. Разрешённый EXECUTE
  сверяется по схеме и **имени** функции, а не по сигнатуре. Перегрузка, например
  `public.app_bot_payment_lookup(text) SECURITY DEFINER`, с `GRANT EXECUTE … TO feelings_billing` проходит страж, хотя
  правило 6 обещает остановку на «другие функции». Создать такую функцию может только тот, у кого есть `CREATE` на
  `public` (владелец или суперпользователь), поэтому MINOR. Ожидается: сверка по
  `p.oid = to_regprocedure('<полная сигнатура>')` (как `BOT_FUNCS` в тестах). Тест —
  `test_r4_guard_stops_remaining_r6_gaps[overload_of_bot_function_name]`, `xfail(strict=True)`.
- **[MINOR] A8-4.4-D6** — там же. Владение объектами проверяется только для `pg_class`, `pg_proc`, `pg_namespace`,
  `pg_type`, больших объектов и базы. Не проверяются:
  - владение сортировкой (`pg_collation`), публикацией (`pg_publication`), внешним сервером
    (`pg_foreign_server.srvowner`), словарём/конфигурацией поиска, оператором, объектом статистики
    (`pg_statistic_ext`);
  - права на табличные пространства (`pg_tablespace.spcacl`).

  Пути к данным через эти объекты не найдено: прав на таблицы у роли нет. Но docstring правила 6 и `docs/ADMIN.md`
  обещают остановку при «владении объектами». Ожидается одно из двух: дополнить `_GRANTS` (проще всего — через
  `pg_shdepend` с `deptype = 'o'`/`'a'` для `refobjid = v_billing`, где учтены и владение, и ACL любых объектов текущей
  базы и общих объектов), либо сузить формулировку в docstring и ADMIN.md. Тесты —
  `test_r4_guard_stops_remaining_r6_gaps` ×7, `xfail(strict=True)`.
- Замечание R10 (Б-97): R5 проверяет атрибут `rolinherit` роли входа бота, но не опцию выдачи. В PG 16 атрибут лишь
  задаёт значение по умолчанию для новых выдач. Выдача `GRANT feelings_billing TO feelings_billing_login WITH INHERIT
  TRUE` проходит, и роль входа получает права `feelings_billing` без `SET ROLE`. Вреда нет: тела функций бота
  требуют `current_setting('role') = 'feelings_billing'`, проверено вручную. Предлагаю добавить в правило 5 проверку
  `pg_auth_members.inherit_option` для пары login → billing, если Б-97 требует `INHERIT FALSE` для выдачи.
- Замечание R11: членство роли приложения или посторонней роли в роли-суперпользователе
  (`GRANT postgres TO feelings_api WITH SET TRUE`) страж не видит: `pg_has_role(…, 'feelings_billing', …)` даёт false.
  Это равносильно выдаче суперпользователя и вне задачи стража. Стоит убедиться, что проверка ролей входа (Б-97,
  `test_login_roles*`) запрещает членство в суперпользовательских ролях.
- Замечание R12: исключение `current_user` в правиле 7 делает результат зависимым от того, кто запускает Alembic.
  Роль с ADMIN-only, запустившая Alembic сама, правило 7 не остановит. Правило 4 остановит её после эскалации до SET.
  На стенде миграции исполняет `feelings_owner`, поэтому это только замечание. Тест A1
  `test_billing_guard_allows_admin_of_migration_runner` закрепляет поведение как задуманное.
- Замечание R9 (р.3, mypy по `tests/test_subscription_db.py:761`) больше не воспроизводится: mypy по файлам A8 чист.

BLOCKER и MAJOR нет.
