## 2. Тесты A8, изменённые A1 (`git show aac7896 -- backend/tests/test_subscription_a8.py`)

Обе правки проверены расчётом по правилу АР-50 п.4 (0020): новый период длится, пока не наберёт `period_days`
времени, не покрытого другими периодами. Ослаблений нет, ожидания строгие, **подтверждаю обе**.

- **`test_r2_refund_all_but_future_then_two_payments`.** Исходное состояние: P1 [t0, t0+30], P2 [t0+30, t0+60],
  P3 [t0+60, t0+90]; P1 и P2 возвращены; P4 оплачен в момент t4 = t0+δ.
  - P4 = [t4, t4+30]. P3 начинается после t4+30, перекрытия нет — проверка `p4 ≈ p1 + δ` осталась прежней.
  - P5 начинается в конце P4 (t0+30+δ). Естественный конец — t0+60+δ, P3 начинается раньше. Поэтому конец
    продлевается на длину P3 (30 дней) и равен t0+90+δ = `p3_end + (p4_end − p1_end)`.
  - Непокрытое время P5: [t0+30+δ, t0+60] = 30−δ и [t0+90, t0+90+δ] = δ, итого ровно 30 дней.
  - Статус `active` с концом цепочки `max(P3, P5) = P5` — верно.
  - Прежнее ожидание (`P5 = P4 + 30`, конец цепочки = конец P3) — это как раз потеря δ, MAJOR-2.
  - Равенство точное: обе части считаются в базе.
- **`test_r2_downgrade_upgrade_switches_period_rule_and_keeps_dates`.** Исходное состояние: P1 [t0, t0+30]
  возвращён, P2 [t0+30, t0+60], период «старого правила» [t0+60, t0+90] (оплачен под 0018 после отката).
  - P4 оплачен в t4 = t0+δ. Цепочка, которая начинается внутри естественного конца, — P2 и старое правило подряд,
    60 дней. Значит, P4 = [t4, t4+90].
  - Непокрытое время: [t4, t0+30] = 30−δ и [t0+90, t4+90] = δ, итого 30 дней.
  - Новые границы `before + 90 д ≤ end ≤ after + 90 д` и статус `active` с концом P4 верны.
  - Строгость не снижена: границы по-прежнему ограничены временем вызова с обеих сторон.

Остаток (не дефект): в докстроке второго теста осталось «следующая оплата начинается сейчас и даёт доступ». Это
по-прежнему верно, но о продлении в ней не сказано — пояснение есть в комментарии.

## 5. Дефекты и замечания

- **[MINOR] A8-4.4-D4** — `backend/migrations/billing_guard.py:68-80` (правила 4 и 5). Страж допускает ADMIN без
  SET/INHERIT у **любой** не-суперпользовательской роли, кроме четырёх ролей приложения по имени. А АР-50 п.7 и
  docstring стража допускают его только у **владельца схемы** («так владелец получает созданную им роль»). Кроме
  того, страж не проверяет:
  - ADMIN OPTION у самой `feelings_billing_login`;
  - кто является членом `feelings_billing_login` в режиме только ADMIN.

  Воспроизведено (тест `test_r3_admin_holders_escalate_and_next_run_catches` ×4, зелёный):
  1. Посторонняя роль входа с `ADMIN TRUE, INHERIT FALSE, SET FALSE` → страж проходит → роль сама делает
     `GRANT feelings_billing TO себе WITH SET TRUE`.
  2. Роль входа с INHERIT в группу, у которой ADMIN-only → `GRANT … GRANTED BY группа` → SET.
  3. `feelings_billing_login` с ADMIN OPTION → бот выдаёт `feelings_api` SET на `feelings_billing`, и сессия
     пользователя после этого может вызывать функции бота.
  4. Посторонний с ADMIN-only на `feelings_billing_login` → выдаёт себе SET на роль входа бота, а через неё —
     SET на billing.

  Под угрозой роли входа из `roles.sql` с переменными именами (`feelings_worker_login`, `feelings_admin_login`)
  и любые посторонние роли кластера.

  Почему MINOR, а не MAJOR:
  - нужна заранее выданная ADMIN OPTION;
  - роль с ADMIN должна сама совершить действие — пассивного обхода, как в D3, нет;
  - итоговое состояние (SET у постороннего или у `feelings_api`) страж ловит на **следующем** запуске Alembic
    (проверено в том же тесте). Окно открыто до следующего `alembic upgrade`.

  Ожидается:
  - ADMIN-only на `feelings_billing` — только у роли, исполняющей миграции (`current_user`), или у владельца
    схемы `public`;
  - у `feelings_billing_login` — без ADMIN OPTION на `feelings_billing`;
  - в `feelings_billing_login` не входит никто, кроме суперпользователей, ни в каком виде (`pg_has_role(…,
    'MEMBER')`).

  Тесты: `test_r3_guard_stops_admin_outside_schema_owner` ×4, `xfail(strict=True)`. Если оператор сочтёт
  ADMIN-доверие любой роли допустимым, это нужно записать в АР-50 п.7 явно, а xfail — перевернуть.

- Замечание R5 (Б-97, A7): страж проверяет у `feelings_billing_login` только SUPERUSER. `INHERIT`, `CREATEROLE`,
  `CREATEDB`, `BYPASSRLS` проходят, хотя Б-97 требует `LOGIN NOINHERIT`. Вреда в текущей схеме не найдено.
  Предлагаю проверять эти атрибуты в страже или в проверке `roles.sql` (Б-97), когда появится роль входа бота.
- Замечание R6: права `feelings_billing` на таблицы и последовательности (п.7: «без прав на таблицы») ни страж, ни
  тесты не проверяют. `GRANT SELECT ON users TO feelings_billing` проходит незамеченным, и роль входа бота получила
  бы чтение. Предлагаю A1 добавить в страж или в каталог-тест: у `feelings_billing` нет привилегий ни на одно
  отношение схемы.
- Замечание R7: страж исполняется и при `alembic downgrade`. Испорченная роль блокирует и откат — в том числе
  аварийный откат 0020 на стенде. Это разумно (сначала исправить роль), но стоит описать в `docs/ADMIN.md` вместе с
  Б-97.
- Замечание R8: при `feelings_billing_login` с SUPERUSER сообщение стража перечисляет все роли кластера («входит в
  другие роли: feelings_admin, …, postgres») — вводит в заблуждение. Остановка верная, косметика.
- Замечание R9: mypy по `tests/test_subscription_db.py:761` (A1) — ошибка типов; `make lint` её не видит, потому
  что не проверяет тесты.
