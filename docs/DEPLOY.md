# Выкладка тестового стенда (задача 0.8)

Инструкция для оператора. Комплект лежит в `infra/deploy/`. Сервер находится в РФ (152-ФЗ, Д1);
снаружи открыты только 80/443 и SSH. Данные на стенде только выдуманные или тестовых
пользователей — никакой продуктивной переписки. Каждый шаг, который меняет стенд, выполняется
**только после подтверждения оператора** (RoadMap §4):

- миграции БД;
- установка вебхука;
- откат схемы.

Роли, ключи, переменные окружения и ротация описаны в `docs/ADMIN.md`.

| Файл | Что |
| --- | --- |
| `infra/deploy/bootstrap.sh` | Подготовка Ubuntu 22.04/24.04: Docker, ufw, пользователь `feelings`, `/opt/feelings` |
| `infra/deploy/docker-compose.prod.yml` | Caddy (HTTPS, Mini App), API, воркеры, PostgreSQL 16 + pgvector, Redis; профиль `ops` — миграции и роли |
| `infra/deploy/Caddyfile`, `caddy.Dockerfile` | Прокси, сертификат Let's Encrypt, заголовки безопасности, пределы тела, сборка Mini App |
| `infra/backend.Dockerfile` | Образ API и воркеров (пользователь без прав, uid 10001) |
| `infra/deploy/.env.prod.example` | Шаблон переменных без значений, с командами генерации |
| `infra/deploy/gen_secrets.py` | Заполняет пустые секреты в `.env`, ничего не печатает |
| `infra/db/roles.sql` | Роли входа API, воркера и администратора |

Все команды `docker compose` ниже выполняются из `/opt/feelings/app` как пользователь `feelings`.
Для краткости:

```bash
alias dc='docker compose -f infra/deploy/docker-compose.prod.yml'
```

> Значения из `.env`, в том числе пароли и ключи, показывают `dc config`, `docker inspect`
> и `env` внутри контейнера. Их вывод не прикладывайте к тикетам и чатам, не запускайте эти
> команды в записываемом сеансе.

## 0. Решения до начала

1. **Контакты помощи (АР-33).** `FEELINGS_ENV=staging` включает проверки продуктива. В частности,
   `check_help_contacts_config` пропускает без проверенного списка только `dev`/`test`/`local`,
   и с `"verified_by_operator": false` в `backend/app/help_contacts.json` API на стенде
   **не стартует**. Варианты:
   - **(рекомендуется)** оператор проверяет список и вносит линии помощи до выкладки
     (`docs/ADMIN.md` §8). На стенде будут тестовые пользователи, и кризисный ответ должен вести
     на проверенные номера;
   - либо решением оператора в `docs/DECISIONS.md` добавить `staging` к непродуктивным окружениям
     в `app/help.py`. Это правка backend (A1/A2), и тогда стенд показывает непроверенный список
     (только 112).

   `FEELINGS_ENV=dev` на стенде **не использовать**: он разрешает `app.bot.poll`, а тот удаляет
   вебхук бота.
2. **Отдельный тестовый бот** в @BotFather, не продуктивный.
3. **Ключ OpenRouter** для стенда. Без него ответы агента приходят ошибкой, а воркер памяти не
   стартует.

## 1. DNS

Создайте A-запись `стенд.домен` с IP-адресом сервера (и AAAA, если есть IPv6). Дождитесь, пока
`dig +short стенд.домен` вернёт этот IP: Caddy получает сертификат при первом запуске, и порт 80
должен быть доступен снаружи.

## 2. Подготовка сервера

```bash
# под root (или через sudo); скрипт можно скачать из репозитория или скопировать с машины оператора
sudo bash bootstrap.sh
```

Скрипт идемпотентен и делает следующее:

- ставит Docker из официального репозитория;
- настраивает ufw: открыты 22/tcp, 80/tcp, 443/tcp и 443/udp;
- создаёт пользователя `feelings` без пароля, члена группы docker;
- создаёт каталоги `/opt/feelings` (750) и `/opt/feelings/backups` (700).

Затем:

1. Добавьте ключ SSH оператора в `/home/feelings/.ssh/authorized_keys` (права 600).
2. Войдите как `feelings` и клонируйте репозиторий в `/opt/feelings/app`. Для закрытого
   репозитория нужен ключ развёртывания только на чтение.

Членство в группе docker равносильно root на этом сервере, поэтому ключ пользователя `feelings`
храните как ключ администратора. Вход под root по SSH после этого лучше запретить
(`PermitRootLogin no`).

## 3. Переменные окружения

```bash
cd /opt/feelings/app
python3 -I infra/deploy/gen_secrets.py      # создаёт infra/deploy/.env (600), печатает только имена
nano infra/deploy/.env                       # заполнить вручную недостающие значения
```

`gen_secrets.py` генерирует только пустые значения и заданные не трогает; повторный запуск
безопасен. Он заполняет:

- пароль `postgres`;
- пароли трёх ролей входа;
- секрет вебхука;
- секрет сессии;
- ключ шифрования;
- ключ отпечатков;
- хеш токена администратора.

Сам токен администратора скрипт кладёт в `infra/deploy/admin-token.txt` (600): передайте его
администратору защищённым каналом и удалите файл.

Вручную задаются:

- `FEELINGS_DOMAIN`;
- `FEELINGS_ACME_EMAIL`;
- `FEELINGS_TELEGRAM_BOT_TOKEN`;
- `FEELINGS_BOT_USERNAME`;
- `OPENROUTER_API_KEY`.

`FEELINGS_ENV=staging` уже стоит в шаблоне.

**Резервная копия секретов:** сохраните копию `.env` (а главное — ключи шифрования и отпечатков)
в хранилище секретов отдельно от сервера и от копий БД. Без ключей копия БД бесполезна, а потеря
ключа отпечатков возвращает удалённые записи памяти (`docs/ADMIN.md` §6).

## 4. Сборка и запуск БД

```bash
dc build                      # образы feelings-backend и feelings-caddy (метка FEELINGS_IMAGE_TAG)
dc up -d postgres redis
dc ps                         # postgres — healthy
```

## 5. Миграции и роли — ТОЛЬКО по подтверждению оператора

Миграции стенда — общий стенд (АР-4), поэтому запускаются только после явного подтверждения
оператора:

```bash
dc --profile ops run --rm migrate      # alembic upgrade head под владельцем схемы
dc --profile ops run --rm db-roles     # роли входа: feelings_api, feelings_worker_login, feelings_admin_login
```

`db-roles` в конце проверяет, что каждая роль входа может стать только своими ролями.
Повторный запуск безопасен; с новыми паролями в `.env` он выполняет ротацию.

## 6. Запуск сервисов

```bash
dc up -d                      # caddy, api, worker-memory, worker-kb (+ postgres, redis)
dc ps                         # api — healthy, воркеры — running
curl -fsS https://стенд.домен/api/v1/health    # {"status":"ok"}
dc logs --tail=50 api worker-memory worker-kb caddy
```

Проверьте:

- **Сертификат:** `curl -vI https://стенд.домен/ 2>&1 | grep -i 'issuer\|strict-transport'`.
- **Порты:** снаружи (`nmap -Pn -p 1-65535 стенд.домен`) открыты только 22, 80 и 443.
- **Падение API при старте:** чаще всего это непроверенный список контактов (шаг 0) или пустой
  секрет. В журнале будет имя переменной без значения.
- **Остановка воркера памяти после пяти попыток:** почти всегда это `OPENROUTER_API_KEY`
  (`dc logs worker-memory`).

## 7. Вебхук бота — по подтверждению оператора

Бот работает по вебхуку на том же API (`POST /api/v1/telegram/webhook`). Подлинность запроса
проверяется по заголовку `X-Telegram-Bot-Api-Secret-Token`. Регистрация выполняется внутри
работающего контейнера API: секреты берутся из его окружения и не печатаются.

```bash
dc exec api python -m app.bot.setup --webhook-url https://стенд.домен/api/v1/telegram/webhook
```

Команда задаёт:

- кнопку меню Mini App (`FEELINGS_WEBAPP_URL` = `https://стенд.домен/`);
- команды `/start` и `/help`;
- вебхук с секретом.

Проверка: напишите боту `/start`, ответ должен прийти с кнопкой открытия Mini App.
Режим опроса (`app.bot.poll`) на стенде запрещён (`FEELINGS_ENV=staging`) и удалил бы вебхук.

## 8. Обновление

```bash
cd /opt/feelings/app
git fetch && git checkout <коммит или тег>
# FEELINGS_IMAGE_TAG в .env = короткий хеш коммита — прежние образы остаются для отката
dc build
# если в обновлении есть новые миграции — сначала резервная копия (раздел 10),
# затем по подтверждению оператора: dc --profile ops run --rm migrate
dc up -d
curl -fsS https://стенд.домен/api/v1/health
```

Если в обновлении изменился `infra/db/roles.sql`, запустите `dc --profile ops run --rm db-roles`.

## 9. Откат

- **Без изменений схемы:** верните прежнюю метку `FEELINGS_IMAGE_TAG` в `.env` и выполните
  `git checkout <прежний коммит>` и `dc up -d`. Пересборка не нужна, если образ с этой меткой
  остался.
- **Схема менялась:** только по подтверждению оператора.
  1. Остановите API и воркеры: `dc stop api worker-memory worker-kb`.
  2. Сделайте резервную копию (раздел 10).
  3. Выполните `dc --profile ops run --rm migrate alembic downgrade <ревизия>`, затем верните
     прежние образы.

  Если downgrade недоступен или опасен, восстановите БД из копии, снятой перед обновлением
  (раздел 10).
- **Вебхук:** при откате остаётся прежним (адрес тот же).

## 10. Резервная копия БД (вручную, до задачи 4.7)

Автоматического резервного копирования пока нет (ТЗ §10: ежедневно, хранение 30 дней,
проверка восстановления раз в квартал — задача 4.7). До неё копию снимают вручную, обязательно
перед каждой миграцией и обновлением:

```bash
umask 077
dc exec -T postgres pg_dump -U postgres -Fc feelings > /opt/feelings/backups/feelings-$(date +%F-%H%M).dump
ls -l /opt/feelings/backups/
```

- Тексты в копии зашифрованы ключами приложения, а метаданные — нет. Храните копии только в РФ,
  с правами 600, и не дольше 30 дней (удаление аккаунта должно доходить и до копий, ТЗ §9).
- Роли кластера в `pg_dump` не входят. После восстановления запустите `db-roles`.

Проверка восстановления (на стенде, по подтверждению оператора):

```bash
dc exec -T postgres createdb -U postgres feelings_restore_check
dc exec -T postgres pg_restore -U postgres -d feelings_restore_check --no-owner < /opt/feelings/backups/<файл>.dump
dc exec -T postgres psql -U postgres -d feelings_restore_check -c "SELECT version_num FROM alembic_version"
dc exec -T postgres dropdb -U postgres feelings_restore_check
```

## 11. Что запрещено на стенде

- Подключать продуктивного бота или реальную переписку.
- Публиковать порты БД и Redis. Менять `ports:` можно только у `caddy`.
- Запускать `roles.sql` с ключами psql `-a`, `-e`, `-E`.
- Включать журнал доступа Caddy: в пути `/invites/<токен>` есть токен приглашения.
- Запускать несколько процессов API. Защита от повторной доставки обновлений бота и фоновые
  задачи живут в памяти одного процесса.
