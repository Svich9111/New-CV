## Границы

Входит (`frontend/`):

- Маршрут `chat` (`src/app/routes.ts`), экран `src/screens/Chat.tsx`; состояние чата на всю сессию —
  `src/chat/session.ts` (`ChatSession`, только память): уход в «Помощь» посреди ответа не обрывает поток, «Назад»
  возвращает к той же переписке и недописанному тексту.
- Вход в чат: главный экран «Вы пара» (`Paired.tsx`) — MainButton «Поговорить с агентом» и карточка-ссылка (работает и
  при отказе нативной кнопки); экран приглашения (`Invite.tsx`), пока пара ждёт партнёра, — кнопка «Поговорить с
  агентом» (сервер требует только онбординга; прототип тоже разрешает).
- История `GET /chat/messages`: первая страница (30), «Показать более ранние сообщения» по `next_cursor`; 422 по
  курсору (в том числе после смены ключа сервера, Б-62) — история с первой страницы, прежний курсор не повторяется,
  подпись «Переписку пришлось загрузить заново…».
- Реплика `POST /chat/messages` и поток SSE (`src/api/chat.ts` — разбор по стандарту SSE, `src/api/client.ts` —
  `chatSend`): куски `delta` по мере прихода, `done`, `crisis`, `error`; комментарии-пинги; поток по частям любой длины
  (граница посреди строки, `\r\n`, многобайтного символа) и целиком; реализация fetch без потокового тела.
- «Агент пишет…» до первого куска и подписью под растущим ответом; «Остановить» (отмена потока, сервер отменяет вызовы
  модели); обрыв, срок тишины (45 с, сервер шлёт пинг раз в 15 с), испорченный поток — понятное состояние подписью.
- Повтор без дубля реплики (АР-51, см. заметки): ключ `client_message_id` на каждую новую реплику, тот же ключ при
  повторе; `accepted` — привязка пузыря к записи сервера; после сбоя с неизвестным исходом — сверка с первой страницей
  истории по ключу и `reply_to`; 409 «ответ ещё готовится» — автоповтор через паузы; 422 под ключом — понятная ошибка.
- Кризис: текст протокола целиком (`replace` — замена показанного), контакты помощи прямо под ответом (номера ссылками
  `tel:`, 112 всегда), «Все контакты помощи»; испорченное событие `crisis` — свой текст и 112; ответ с `crisis: true` в
  истории — тот же блок (контакты из `GET /help/contacts`, без них — 112).
- Дневной лимит 429: свой текст со временем по `Retry-After` (часы устройства и «через N»), реплика сохранена, поле
  ввода не блокируется (кризис сервер принимает и сверх лимита).
- Пометка приватности на экране: «Этот разговор видишь только ты. Партнёр и его агент его не видят…».
- Строгие проверки вида ответов (как в 1.5): `ChatMessage` (с `client_message_id`, `reply_to`, `crisis`), страница
  истории, события потока (с `accepted`).
- Б-93 (попутно, `src/boot.tsx`, `index.html`): внутри Telegram экран ожидания с «Помощью» — сразу; срок
  `SDK_GIVE_UP_MS` — от запуска; в заглушке `#root` — `tel:112`.

Не входит: сервер и контракт (предложения — ниже, для A1), голос, черновик, лента пары, подписка, проверка на телефоне.

## Критерии готовности

- [x] История с подгрузкой по курсору; 422 по курсору — с первой страницы без повтора прежнего курсора; ответ не по
      схеме — «История пришла с ошибкой», ничего чужого на экране.
- [x] Реплика: пустая и из пробелов не уходит, предел 4000 (счётчик с 3500); Enter — отправить, Shift+Enter — строка;
      двойное нажатие (второе касание попадает в «Остановить») и Enter во время ответа — одна реплика.
- [x] Потоковый ответ по контракту (по частям, целиком, по 1 байту); «Агент пишет…»; завершение по `done`.
- [x] Отмена и обрыв — состояние подписью («Ответ остановлен и не сохранён», «Ответ прервался…», «Сообщение
      сохранено, ответа нет», «Не отправлено»); повтор тем же пузырём и тем же ключом (сервер новой реплики не создаёт,
      АР-51); ответ, сохранённый сервером до обрыва, показан без повторной отправки; сверка — по ключу и `reply_to`, не
      по тексту (одинаковые реплики подряд различаются, реплика с другого устройства не принимается за свою, сверка без
      загруженной истории не делает вывода по чужим записям).
- [x] Кризис — без смягчения, контакты помощи (из события, 112 всегда) сразу на экране; не блокируется лимитом; после
      нового открытия чата и перезагрузки истории — тоже (`crisis: true`; кризисный ответ без id сохраняется локально).
- [x] 429 — свой текст с временем; 409 `conflict_retry` — один немедленный повтор, затем сверка: реплики нет — «Не
      отправлено», ответ сохранён — показан, ответ ещё готовится — автоповтор с тем же ключом через 3, 6, 10 с, затем
      «Повторить»; 422 под ключом — «Сервер не принял это сообщение…», повтор с новым ключом; 401 — один повторный вход;
      `error` — текст по коду, незнакомый код — `internal`.
- [x] Ответ агента — только текст React (переносы — CSS `pre-wrap`); `dangerouslySetInnerHTML`/`innerHTML` в исходниках
      нет (тест); XSS в ответе и реплике — текст.
- [x] Приватность: тексты не попадают в консоль, хранилища браузера, cookie и адрес; пометка приватности на экране.
- [x] Доступность: экранный диктор слышит «Агент пишет…», затем ответ целиком (`aria-live="polite"`), куски потока не
      зачитываются; растущий пузырь — `aria-busy`; ошибки — `role="alert"`; у поля и кнопок — доступные имена.
- [x] Нативные элементы: MainButton на главном экране, BackButton из чата; запасные кнопки в странице; отклик —
      `impact` на нажатие, `notification:error` на сбой.
- [x] Красный — только MainButton и сердце; ошибки — нейтрально (`theme.test.ts`).
- [x] Б-93: экран ожидания с «Помощью» сразу, срок от запуска, 112 в заглушке.
- [x] `npm run lint` (eslint + tsc + свежесть `schema.d.ts` по рабочему контракту), `npm test` ×2, `npm run build` —

## Заметки A4

- **Повтор без дубля реплики (АР-51, часть 2).** Каждая новая реплика получает ключ `client_message_id`
  (`newMessageKey`: `crypto.randomUUID`, в старых WebView — uuid v4 из `getRandomValues`); «Повторить», «Отправить ещё
  раз», «Проверить и повторить» и автоповтор после 409 шлют её с тем же ключом — сервер новой реплики не создаёт.
  `accepted` привязывает пузырь к id записи; растущий ответ получает `reply_to`. (1) Пока ответ идёт, вторая реплика не
  уходит. (2) После сбоя с неизвестным исходом (нет связи, срок, 5xx, обрыв, «Остановить», испорченный поток) клиент
  перечитывает первую страницу и ищет **свою реплику по ключу** (или по id из `accepted`), **ответ — по `reply_to`**:
  ответ есть — показан он, без повторной отправки; реплики нет — «Не отправлено»; реплика без ответа — «Повторить»;
  история не читается — «Проверить и повторить». Тексты не сравниваются, поэтому одинаковые реплики подряд — разные
  пузыри, реплика с другого устройства (свой ключ) встаёт отдельным пузырём по порядку сервера (MINOR-4), а без
  загруженной истории сверка не принимает старую запись за новую (MAJOR-2); прочитанная сверкой страница становится
  первой страницей ленты, уведомление об ошибке истории снимается. (3) `error`, 429, 402 — реплика сохранена; если
  `accepted` пришёл с `message_id: null`, при `error` — «Не отправлено» со строкой о помощи (АР-34 п.2). (4) 409 после
  немедленного повтора — сверка: реплики нет (транзакция, АР-24) — «Не отправлено»; ответ сохранён — показан; реплика
  без ответа (ответ готовит прежняя попытка) — «Агент пишет…» и автоповтор через 3, 6, 10 с (`REPLY_WAIT_MS`),
  «Остановить» прерывает паузу; потом «Ответ на это сообщение ещё готовится. Повтори чуть позже…» и «Повторить».
  (5) 422 при проверенном тексте — сервер не принял ключ (под ним другой текст): «Сервер не принял это сообщение.
  Отправь его ещё раз — оно уйдёт как новое.», повтор — с новым ключом. (6) Ответ на реплику, повторённую после других
  (сервер ставит его по времени сохранения), на экране — сразу под своей репликой (`visibleItems` по `reply_to`).
  **Свёртка одинаковых реплик осталась только для записей без ключа** (до миграции 0018: подряд, один текст, без
  ответа между ними); записи остаются в выгрузке (ФТ-21).
- **Строгость `accepted`.** С ключом `accepted` должен прийти первым и один раз, с тем же ключом; `delta`/`done` до
  него, второй `accepted`, чужой ключ, поле не того вида — `bad_response` (дальше — обычная сверка по истории).
  Кризис принимается и без `accepted` (помощь при любом виде потока, §9.3). Без ключа (`chatSend` без
  `clientMessageId`) `accepted` по контракту не бывает и пропускается как незнакомое событие — так страж A8
  «незнакомые события (accepted, ping, …)» остаётся в силе без правки.
- **Строгость `ChatMessage`.** `client_message_id`, `reply_to`, `crisis` обязательны; ключ — непустая строка или `null`
  и только у владельца; `reply_to` и `crisis: true` — только у агента. Запись не по контракту — вся страница
  «История пришла с ошибкой», как раньше.
- **Лимит 429 не блокирует ввод**: при кризисе сервер отвечает протоколом и сверх лимита (§9.3, §11 п.5); если бы
  клиент закрыл ввод до конца окна, человек в кризисе не получил бы ответа. Текст это говорит прямо.
- **В чате нет MainButton**: в прототипе главная кнопка чата — «Подготовить сообщение…» (3.1/3.4); отправка агенту —
  круглая кнопка в поле ввода (тёмная, не красная), как в прототипе. «Помощь» в чате — в закреплённом низу под полем
  ввода (видна при любой длине ленты, как в прототипе N-3), общая ссылка каркаса на этом экране скрыта.
- **Кризисный ответ в истории** (MINOR-3, предложение 3 принято): у ответа с `crisis: true` — тот же блок «Помощь
  рядом»; контакты — один запрос `GET /help/contacts` на сессию (в истории их нет), пока не пришли или при сбое —
  пустой список, экран показывает 112. Контакты, пришедшие в событии `crisis`, при перезагрузке истории сохраняются
  по id; кризисный ответ без id (`message_id: null`) при перезагрузке после 422 остаётся в ленте (раньше пропадал).
  Ответы, сохранённые до миграции 0018, — с `crisis: false`, без блока; «Помощь» внизу экрана есть всегда.
- Сообщение `error` сервера (на «вы», при отсутствии вердикта — с фразой о помощи, АР-34) не показывается: клиент
  показывает свой текст по коду, а под подписью **любой** ошибки `error` (в том числе `refusal`) — своя строка о помощи
  (АР-34 п.2, ревью р.1 MAJOR-3): «Если тебе сейчас опасно или очень тяжело — звони 112» (`tel:112`) и «Все контакты
  помощи». Совета «скажи иначе» больше нет: `refusal` — «Агент не смог ответить на это сообщение. Можно повторить.»
- **Прокрутка ленты** (р.1, A8-2.2-D4). Окно — прокручиваемый документ, низ с полем ввода закреплён (`sticky`).
  Экран меряет высоту закреплённого низа (`ResizeObserver`) и ставит её в `--chat-bottom-h`; метка конца ленты
  (`.chat-end`) прокручивается с `scroll-margin-bottom` = эта высота + 12 px — последний пузырь всегда над полем.
  «Прилипание» к низу считается по событию `scroll` (то есть до роста пузыря, а не после). Своя отправка и «Повторить» —
  к концу всегда; начало и куски ответа — к концу, если лента прилипла; человек ушёл читать выше — не дёргаем, в
  закреплённом низу кнопка «К новым». Кризис — всегда: ответ с блоком «Помощь рядом» целиком над полем, а если он
  выше окна — блок помощи с начала. Подгрузка более ранних сверху к концу не прокручивает. Клавиатура телефона
  (смена высоты окна) — прилипшая лента остаётся у низа. Проверено в Chromium по `dist` (375 px, светлая и тёмная).
- **Лимит 429, текст** (р.1, MINOR-1): «…всё равно напиши: на такое сообщение тебе ответят и сверх лимита и подскажут,
  куда обратиться. Экстренная помощь — 112 (`tel:112`), контакты помощи доступны всегда.» Обычного ответа не обещает.

- 422 по старой странице посреди отправки: перезагрузка ленты сохраняет реплику идущего обмена и её недописанный ответ;

  новых обменов, а агент отвечал бы на неё уже после них (в контексте модели — более поздние реплики), то есть ответ
  был бы не на тот разговор, который видит человек; (2) принцип 2 ТЗ — реплика уходит только по явному «Отправить»
  для текущей мысли: прежняя «Не отправлено», отправленная после следующей реплики, пришла бы агенту не в том порядке,
  в каком человек её писал; переписать её заново — явное новое действие; (3) у сессии одна сверка и одно состояние
  повтора (`Turn`: ключ, `before`, паузы 409) — повтор чужого обмена требовал бы хранить их на каждую реплику без
  пользы для человека. Сервер по АР-51 ответил бы и на старый ключ, поэтому (б) остаётся возможным позже, если
  оператор попросит. Кнопка «Повторить» больше не бывает «мёртвой»: `retry` по-прежнему молча выходит при чужом
  ключе, но экран такую кнопку не показывает.

  проверяет пустоту строже сервера, отдельный код ничего не меняет на экране.
- **Раунд 4. Допущение сверки по старым страницам (MINOR-R3-2).** Если своя реплика найдена сверкой не на первой
  странице истории (с другого устройства за время ответа пришло больше страницы записей, О-4), в ленту встаёт только
  первая страница сверки и найденный ответ на свою реплику; записи между ней и своей репликой (2-я…N-я страницы) до
  нового открытия чата не видны, «Показать более ранние» их не подгрузит (курсор ленты прежний), а свой пузырь стоит
  ниже более новых записей. Принято сознательно: случай редкий (больше `PAGE` записей с другого устройства за один
  ответ), данные только свои, при новом открытии порядок сервера восстанавливается (`session.a8r2`), подпись у своей
  реплики верная. Разрыв в ленте («есть более ранние сообщения — загрузить») не делается; если понадобится, вместе с ним
  пересматриваются проверки A8 р.3 «О-4: более старые страницы сверки только для подписи» (`session.a8r3.test.ts`).

## Предложения к контракту (для A1)

Итог (АР-51): **1–3 приняты** (`accepted`, `client_message_id`, `crisis`/`reply_to` в истории) и реализованы в части 2;
**4–5 не приняты** — клиент по-прежнему показывает строку о помощи под любой ошибкой `error` и считает время лимита по
`Retry-After`.


1. **id реплики владельца в потоке**: первое событие `accepted {message_id}` (или заголовок ответа) — клиент сверял бы
   историю по id, а не по тексту.
2. **Повтор без новой реплики**: `POST /chat/messages/{message_id}/reply` (ответ на уже сохранённую реплику без ответа)
   или ключ идемпотентности `client_message_id` в теле `POST /chat/messages` — тогда свёртка повторов на экране не нужна.
3. **Кризис в истории**: поле `crisis: true` у `ChatMessage` агента — при новом открытии чата показать контакты под
   кризисным ответом (§9.3 «всегда»).
4. **Подсказка о помощи в `error`**: вместо фразы в `message` (на «вы») — флаг `help_hint: true`, клиент покажет свой
   блок помощи.
5. **Время конца окна лимита** в теле 429 (`window_resets_at`, как в черновике `limits` задачи 4.4) — время на экране не
   зависело бы от часов устройства и задержки ответа.
