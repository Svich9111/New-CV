## Границы

Входит: модуль `bot/` (Python, общий `backend/pyproject.toml` или свой — обоснуй): приём обновлений через вебхук
(эндпоинт сервера с проверкой секретного заголовка `X-Telegram-Bot-Api-Secret-Token`), команда `/start` и
`/start <payload>` — ответ с кнопкой открытия Mini App (`web_app`), для `startapp`-ссылок Telegram открывает
Mini App сам — бот лишь отвечает на `/start`; кнопка меню Mini App; клиент Bot API с `sendMessage` для будущих
уведомлений (3.5) — без текста сообщений пары; устойчивость к повторной доставке обновлений (идемпотентность по
`update_id`); журналы без текстов и токенов.
Не входит: уведомления о сообщениях (3.5), оплата (4.4), реальная регистрация вебхука на стенде (0.8).

## Критерии готовности

- [x] Вебхук отклоняет запросы без/с неверным секретным заголовком (401/403), сравнение за постоянное время
  (`hmac.compare_digest`); секрет не настроен — 503 для всех, пустой заголовок не совпадает с пустым секретом.
- [x] `/start` и `/start <любой payload>` → ответ с кнопкой Mini App; payload не попадает в журналы.
- [x] Повторная доставка того же `update_id` не даёт второго ответа. Временный сбой Bot API (429/5xx/сеть) —
  503 и снятие отметки, повторная доставка обрабатывается один раз; постоянная ошибка (403 «бот заблокирован») — 200.
- [x] Неизвестные типы обновлений и команды не роняют обработчик (в т. ч. неверный JSON, нет `update_id`,
  не личный чат — без ответа).
- [x] Токен бота и секрет вебхука — только из окружения; без них сервис не стартует (как в 1.1).
  Также обязателен `FEELINGS_WEBAPP_URL` (https) — без него нельзя построить кнопку `web_app`.
- [x] Клиент Bot API: таймауты, повтор на 429 с `retry_after`, ошибки не содержат токен (токен в URL Bot API!);
  журнал httpx (`HTTP Request: POST <url>`) — через фильтр `app.core.logging`.
- [x] Тесты без сети (подменённый транспорт).
- [ ] Проверка на настоящем тестовом боте — **ждёт токен оператора** (шаги — `bot/README.md`).

Решения по ходу:

- Размещение: вебхук — маршрут сервера `POST /api/v1/telegram/webhook` (`backend/app/bot/webhook.py`), логика —
  пакет `backend/app/bot/`; общий `backend/pyproject.toml` (одни настройки, журналы, выкладка). `httpx` перенесён
  из dev-зависимостей в основные.
- Контракт не менялся: маршрут служебный (`include_in_schema=False`), исключён в `tests/test_contract.py` явным
  списком `SERVICE_ROUTES`. Попутно: `test_implemented_routes_exist_in_contract` при FastAPI 0.165 не видел
  маршрутов из `include_router` (в `app.routes` они — `_IncludedRouter` без `path`) и проверял только `/health`;
  обход исправлен, все маршруты 1.1–1.3 проверку проходят.
- Идемпотентность — в памяти процесса (без новой таблицы БД); при нескольких экземплярах нужен Redis — Б-26.
- Раунд 1 (A8 D-2, A6 m2), повтор во время первой доставки. Выбраны обе меры:
  1) повтор не получает 200 «duplicate», пока первая доставка в работе: он ждёт её исхода
     (`UpdateDeduplicator.wait_outcome`) и отвечает так же — 200, если первая завершилась, 503, если
     она сняла отметку из-за временного сбоя (Telegram доставит снова, обновление не теряется);
  2) общий срок обработки одного обновления `HANDLE_DEADLINE_S = 20` с (`asyncio.timeout` вокруг
     обработчика, повторы 429 и тайм-ауты внутри него; ожидание повтора ограничено тем же сроком) —
     заметно меньше времени ожидания ответа Telegram (порядка минуты); по истечении — 503 и снятие
     отметки. Чистый «503 для любого повтора в работе» отвергнут: при успешной первой доставке
     Telegram получил бы лишнюю повторную доставку (тест A8 `test_concurrent_identical_deliveries_send_once`
     ждёт 200/200). Семантика — «хотя бы один раз»; дубль ответа на `/start` после тайм-аута чтения
     безвреден, для уведомлений 3.5 — Б-27.
- Каркас уведомлений (`app/bot/notifications.py`): только фиксированные шаблоны, параметра для текста нет (ФТ-18).
- Живая проверка без сервера (до 0.8) — режим разработки: `python -m app.bot.poll` (deleteWebhook,
  долгий опрос getUpdates, timeout 25 с; при `FEELINGS_ENV=prod` не стартует), `python -m app.bot.check`
  (getMe), `python -m app.bot.setup --no-webhook`. Обработка обновления вынесена из вебхука в общую
  функцию `app/bot/processing.py::process_update` (исход ACK/RETRY: вебхук — 200/503, опрос — сдвиг
  offset / повтор того же обновления после паузы); offset — только после обработки, при остановке
  обработанные подтверждаются. Конфигурация опроса — `check_dev_bot_config` (токен + https-адрес
  Mini App), `check_bot_config` сервера не менялась. В продуктиве — только вебхук.
