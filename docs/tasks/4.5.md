## Границы

Этап 1 (A1, миграция 0005): функция `app_delete_account()` — SECURITY DEFINER, только для текущего пользователя:
выход из активной/ожидающей пары тем же путём, что `app_leave_couple` (пара распускается для обоих, приглашения отзываются);
полное удаление строки `users` и каскадом — агента, диалогов, памяти, черновиков, приглашений, событий безопасности
этого пользователя; сообщения, которые написал партнёр удаляемому, остаются у партнёра (`recipient_id` → NULL);
сообщения, которые написал удаляемый, удаляются (его данные); `audit_log` — запись `account.delete` без
персональных данных (actor_id = NULL после удаления — опиши выбор); отзыв у `feelings_app` прямого DELETE на `users` (Б-19);
`app_find_invite`/`app_accept_invite` не работают с приглашениями удалённого автора (Б-20 — после полного удаления их
нет, проверь тестом); повторная регистрация того же telegram_id создаёт нового пользователя (Б-3, снять xfail D-7 у A8 —
сделает A8). Этап 2 (A2, после 4.2): `DELETE /me`, `GET /me/export` (только данные владельца, расшифрованные; без памяти и
личного чата партнёра) по контракту.

## Критерии готовности (этап 1)

- [x] После `app_delete_account()` в БД нет ни одной строки с id пользователя (проверка по всем таблицам), кроме обезличенного аудита.
- [x] Пара распущена, партнёр может создать новую; его сообщения удаляемому остаются у него, сообщения удаляемого — удалены.
- [x] Прямого DELETE на users у приложения нет (Б-19); удаление только функцией.
- [x] Повторный вход тем же telegram_id — новый пользователь без следов старого.
- [x] Гонки: удаление одновременно с принятием приглашения / отправкой — без взаимоблокировок, порядок блокировок как в АР-13.
- [x] Миграция обратима; `alembic check` чист; тесты под ролью `feelings_api`.
- [x] Дополнение A0 (Б-38, ревью 4.2 MAJOR-1): приложение не удаляет отправленные черновики и агентов — оригиналы сообщений остаются расшифровываемыми; агент и черновики удаляются только `app_delete_account`.

## Критерии готовности (этап 2)

Контракт (A1, до A2) — ✅ сделан, АР-25. Миграция 0006 (A1, до A2): функция выгрузки сообщений пары с оригиналами (у `feelings_app` нет SELECT на `original_enc`, АР-11).
 схема `AccountExport` для `GET /me/export` вместо `additionalProperties: true`; ответы 401, 403
(не требуется завершённый онбординг — выгрузить и удалить данные можно всегда, как выход из пары, АР-17), 409 `conflict_retry`
для `DELETE /me` (АР-24). Формат выгрузки — JSON, версия формата `export_version`.

- [x] `DELETE /me` вызывает `app_delete_account()` через слой доступа (без SQL в обработчике), 204; затем любой запрос с тем же
  токеном сессии — 401; повтор — 401. Работает без завершённого онбординга. 40P01/40001 → 409 `conflict_retry`, не 500.
- [x] Бот: после удаления не шлёт уведомлений удалённому; если уведомление уже в очереди — получатель не найден, без ошибки в журнале.
- [x] `GET /me/export` — только данные владельца, расшифрованные: профиль и онбординг, профиль агента и настройки тона, свои
  диалоги с агентом и сообщения в них, своя память (с источником), свои черновики, сообщения пары — написанные им (оригинал, статус, `is_adapted`;
  адаптированная версия не выгружается — её делает агент получателя, АР-25 п.3) и полученные им (в той форме, что ему показана, оригинал — только если
  он уже открывал его или по §2 п.3 доступен по запросу — опиши выбор), пара (статус, даты, без данных партнёра кроме имени,
  которым пользователь его назвал), подписка и платежи, где он плательщик. Не входят: память, личный чат, профиль агента и
  `tone_settings` партнёра; `safety_events` — только факт и дата, без внутренних полей.
- [x] Повреждённая строка (`DecryptionError`) не роняет выгрузку: поле `unavailable: true` с кодом причины, без текста и id в журнале.
- [x] Тесты: изоляция (партнёр и посторонний — ни одного своего текста в чужой выгрузке, проверка поиском меток), выгрузка после
  выхода из пары, после удаления — 401; журналы без текстов; ответ без заголовков кэширования (`Cache-Control: no-store`).
