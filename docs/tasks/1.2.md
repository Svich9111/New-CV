## Границы

Входит: `PUT /me/onboarding` по контракту (имя, обращение, имя партнёра, часовой пояс, три согласия, 18+);
создание личного агента пользователя (строка `agents`) при завершении онбординга; зависимость FastAPI
`OnboardedUser` для всех будущих эндпоинтов, требующих онбординга; `GET /me` отражает `onboarding_completed`.
Не входит: тексты соглашений (4.6 — юрист), экраны (1.5), пары (1.3).

## Критерии готовности

- [x] Без всех трёх согласий (`consent_terms`, `consent_data`, `consent_sensitive`) онбординг не завершается — 422.
- [x] `age_confirmed=false` → 403 `underage`, согласия не сохраняются, пишется `safety_events` с типом `underage`
      без личных данных; доступ к сервису не предоставляется (ТЗ §9.3).
- [x] Успешный онбординг: поля и время согласий сохранены, создан ровно один агент; повтор — идемпотентен
      (обновляет поля, второго агента нет).
- [x] Зависимость `OnboardedUser`: без завершённого онбординга — 403 `onboarding_required`. Критерий RoadMap
      «Без согласий доступ к чату закрыт» подтверждается тестом на защищённом маршруте (сам чат — 2.1).
- [x] Валидация длины полей по контракту (1–64), часовой пояс — существующая зона IANA.
- [x] Ответ — схема `Me` контракта; тело запроса не отражается в ошибках; SQL только в `repositories/`.

## Заметки исполнителя (A2)

- Порядок проверок: сначала схема контракта (согласия `const: true`, поля), затем возраст. Запрос
  без согласий и с `age_confirmed=false` получает 422, а не 403, и событие `underage` не пишется.
- `age_confirmed=false` у уже прошедшего онбординг снимает `age_confirmed_at` — доступ закрывается
  (ТЗ §9.3); профиль и согласия из такого запроса не сохраняются.
- Время согласий фиксируется при первом согласии; повтор онбординга его не переписывает.
- Согласия принимаются только как JSON `true` (`StrictBool` и проверка `is True`): `1`, `1.0`,
  `"true"` дают 422. `age_confirmed` — строго булево.
- Строковые поля: пробелы по краям обрезаются. Внутри запрещены символы категорий Unicode `Cc`,
  `Cf`, `Zl`, `Zp` (C0/C1, U+0085, U+2028/2029, U+202E, U+200B, U+FEFF и т.п.). Исключения —
  ZWJ (U+200D) и ZWNJ (U+200C): без них ломаются эмодзи-последовательности и ряд письменностей.
  Значение без единого видимого символа (только пробелы, ZWJ/ZWNJ) — 422.
- Часовой пояс — только из списка `zones` пакета `tzdata`, системный каталог не используется.
  Набор одинаков на всех машинах, `posix/…`, `right/…` и файлы `*.tab` не входят, `Factory`
  исключён.
- Условие «онбординг завершён» задано одной константой `ONBOARDED_SQL`
  (`repositories/users.py`). Её используют `is_onboarded` (OnboardedUser) и `get_me`
  (`GET /me`). Тест проверяет все 16 комбинаций отметок.
- Повторные события `underage` (MINOR-5 A6, D-4 A8) **не исправлены**: нужна правка схемы.
  У `feelings_app` на `safety_events` только INSERT (миграция 0001, политика `safety_insert`),
  поэтому проверить наличие прежнего события из кода приложения нельзя. Выбранный вариант —
  не чаще одного события `underage` на пользователя в сутки. Для него A1 нужна функция
  `app_record_underage()` в новой миграции:
  - `SECURITY DEFINER`, `search_path` закреплён;
  - внутри `pg_advisory_xact_lock` по `app_uid()`;
  - `INSERT … WHERE NOT EXISTS (… type = 'underage' AND created_at > now() - interval '24 hours')`;
  - `GRANT EXECUTE` для `feelings_app`.
  После миграции `record_underage` вызовет эту функцию, а проверка A8
  `test_underage_twice_and_after_onboarding_keeps_profile_closes_access` (`== 2`) поменяется
  на `== 1`. Полное решение — АР-14, ждёт оператора.
- Контракт: в `Error.code.examples` добавлен код `underage` (ответ 403 `/me/onboarding` уже
  ссылается на `Error`). `OnboardedUser` проверен на тестовом маршруте, подключённом только в тесте.
