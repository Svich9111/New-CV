Платёжные настройки (токен бота для платежей, цены, включение оплаты на стенде и в продуктиве) — только после
подтверждения оператора (CLAUDE.md, RoadMap §4). В этой задаче — код и тесты на заглушках: ни реальных платежей,
ни токенов, ни обращений к Telegram из тестов.

## Границы

**Этап 1 (A1, миграция 0017, контракт).** Данные подписки пары: периоды (пробный, оплаченный, возвращённый),
плательщик, журнал платежей и счетов с `telegram_payment_charge_id` (идемпотентность и возврат), без лишних
личных данных; функции SECURITY DEFINER: статус подписки, проверка доступа, пробный период один раз на пару,
счёт, проверка перед оплатой, зачисление идемпотентно по `telegram_payment_charge_id`, отметка возврата, данные
для возврата; RLS — статус видят оба партнёра, посторонние — нет; поведение при распаде пары и удалении
аккаунта; порядок блокировок АР-13/АР-38. Контракт: `GET /couple/subscription` (статус, срок, лимиты, тарифы),
`POST /couple/subscription/invoice` (параметры для `Telegram.WebApp.openInvoice`), ответы 402/409/429/503.
Прежние заготовки `/subscription` и `/subscription/invoice` (0.7) сняты.

**Этап 2 (A5, бот).** Обработка `pre_checkout_query` (`app_bot_payment_precheck`, ответ за 10 с,
`error_message` по коду), `successful_payment` (`app_bot_payment_credit`; повторная доставка обновления —
`duplicate`), `refunded_payment` и возврат `refundStarPayment` (`app_bot_payment_lookup` →
`app_bot_payment_refunded`), команда `/paysupport` (правила Telegram для цифровых товаров), выпуск ссылки
`createInvoiceLink` (XTR, одна позиция цены, пустой `provider_token`, payload — `invoice_id`). Клиент Bot API —
заглушка в тестах. Вызовы — в служебном контексте `user_scope(…, None)` через `backend/app/repositories/`.

**Этап 3 (A2, API и лимиты).** Эндпоинты по контракту; пробный период — `app_subscription_start_trial` при
принятии приглашения (в той же транзакции) и при `GET /couple/subscription`; цены и длина пробного периода —
настройки (`FEELINGS_…`, значения по умолчанию — [уточняется] АР-50); лимиты без подписки в чате (402
`subscription_required` или отдельный дневной лимит без подписки — по ответу оператора) и при отправке
сообщения (`POST /drafts/{id}/send` — 402); кризис — без 402/429 (§11 п.5, АР-30); частота выпуска счетов —
429 (`Retry-After`), FC002 → 429; обновление описаний 402 «не отдаётся до этапа 4» в контракте — через A1.

**Не входит:** автопродление подписками Stars (`subscription_period`), промокоды, оплата не Stars, интерфейс
экрана «Подписка» (A4, после контракта), юридические тексты оферты (4.6), админ-отчёты по платежам (ФТ-20).

Значения, которых нет в ТЗ, — [уточняется], вопросы оператору в DECISIONS.md, АР-50:

| Параметр | Рабочее допущение | Вопрос |
| --- | --- | --- |
| Цена в Stars (месяц, год) | Настройка сервера, значения нет | АР-50 п.1 (§11 п.8, §13 в.6) |
| Длина пробного периода | 7 дней от активации пары (Д6) | АР-50 п.2 |
| Лимиты без подписки | До принятия приглашения — дневной лимит чата; после окончания — [уточняется] | АР-50 п.3 |
| Политика возврата | Возврат вручную по `/paysupport`; `couple_ended` — предложить возврат; периоды не сдвигаются | АР-50 п.4 |
| Автопродление | Нет (разовая оплата периода) | АР-50 п.5 |
| Пробный период | Один на пару (новая пара — новый) | АР-50 п.6 |

## Критерии готовности

Этап 1 (A1):

- [x] Миграция 0017 проходит upgrade → downgrade → upgrade; `alembic check` чист; голова одна — 0017.
- [x] Пробный период — один раз на пару (индекс + блокировка пары), отсчёт от активации; повтор и одновременный вызов обоих партнёров — одна строка.
- [x] Зачисление идемпотентно по `telegram_payment_charge_id`: повтор и одновременная повторная доставка — `duplicate`, один период.
- [x] Оплата во время действующего периода начинается после него; повторная оплата той же ссылки — отдельный платёж и период.
- [x] Статус подписки и оплату видят оба партнёра, посторонний — ничего; ожидающие счета напрямую не видны; прямой записи в `subscriptions`/`payments` нет ни у одной роли.
- [x] Функции бота работают только без `app.user_id`, функции пользователя — только с ним (42501).
- [x] Распад пары: оплаченный период дослуживает обоим, пробный — нет; оплата после распада — `couple_ended`. Удаление аккаунта: `payer_id` → NULL, у пары без участников периоды, счета и платежи удаляются.
- [x] Без взаимоблокировок с удалением аккаунта партнёра (порядок пользователь → пара).
- [x] В `payments` и `audit_log` нет текстов и Telegram ID; в `audit_log` — коды действий и id объектов.
- [x] Контракт валиден (openapi-spec-validator), новые пути и схемы проверены `test_contract.py`.

Этап 2 (A5) и этап 3 (A2) — критерии добавляет A0 перед началом этапа; обязательно: тестовый платёж на
заглушке проходит путь `createInvoiceLink` → `pre_checkout_query` → `successful_payment` → `GET
/couple/subscription` у обоих партнёров (RoadMap «тестовый платёж проходит; статус виден обоим»); кризисный
протокол работает без подписки (тест с истёкшей подпиской); журналы без текстов и без Telegram ID.
